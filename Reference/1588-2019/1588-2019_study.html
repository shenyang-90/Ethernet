1. 协议概述

IEEE Std 1588-2019 定义了 Precision Time Protocol (PTP)，用于在网络化测量和控制系统中实现亚微秒级时钟同步。PTP 通过主从层次结构分发时间，并补偿网络传播延迟。

核心功能：在分布式系统中同步各节点的本地时钟，使其与 Grandmaster 时钟保持一致；支持 Ordinary Clock、Boundary Clock、Transparent Clock 三种主要时钟类型。

1.1 协议范围

功能说明
时钟同步通过 Sync/Follow_Up 消息分发主时钟时间
延迟测量Delay Request-Response (E2E) 或 Peer-to-Peer (P2P) 机制
主从选举BMCA 自动选举 Grandmaster 和主从关系
透明转发Transparent Clock 修正驻留时间，不终止 PTP 消息
亚微秒精度基于硬件时间戳实现高精度同步
PTP 是 分布式协议：没有中央控制器，各节点通过 BMCA 独立决定主从关系。所有时间戳必须在 reference plane（通常靠近 PHY/MAC 边界）捕获。

4. 时钟类型与架构 (Clause 6/7)

4.1 Ordinary Clock (OC)

  • 单个 PTP 端口（portNumber = 1）
  • 在同步层次结构中作为 Master 或 Slave 运行
  • 包含：Local PTP Clock + Local Clock（或共享）
  • 在其单个端口上支持 E2E 或 P2P 延迟机制之一

4.2 Boundary Clock (BC)

  • 多个 PTP 端口（N ≥ 2）
  • 一个端口处于 SLAVE 状态（同步到上游主时钟）
  • 其余端口处于 MASTER 状态（向下游分发时间）
  • 所有非管理 PTP 消息在 BC 处终止（不转发）
  • 可以桥接 E2E 和 P2P 区域

4.3 Transparent Clock (TC)

特性E2E TCP2P TC
状态机无（无 MASTER/SLAVE）无（无 MASTER/SLAVE）
驻留时间测量并累积到 correctionField测量并累积到 correctionField
路径延迟不修正路径延迟通过 Pdelay_Req/Resp 测量每端口 meanLinkDelay
Pdelay 消息透明转发终止 Pdelay 消息
Sync/Follow_Up转发所有，添加 residenceTime仅转发 Sync/Follow_Up，添加 residenceTime + meanLinkDelay
Delay_Req/Resp转发所有，添加 residenceTime丢弃 Delay_Req/Resp
关键区别：E2E TC 只修正驻留时间，路径延迟由端点的 Slave 通过 Delay_Req/Resp 测量；P2P TC 额外修正链路延迟，因此 Slave 不需要发送 Delay_Req。

4.4 Management Node

  • 使用 PTP 管理消息（Clause 15）配置/监控 PTP 实例
  • 支持 GET、SET、COMMAND 动作

7. 延迟测量机制 (Clause 11)

7.1 Delay Request-Response (E2E) (Clause 11.3)

消息：Sync, (Follow_Up), Delay_Req, Delay_Resp

时间戳：

  • t1 = Sync 发送时间戳（Master 时间）
  • t2 = Sync 接收时间戳（Slave 时间）
  • t3 = Delay_Req 发送时间戳（Slave 时间）
  • t4 = Delay_Req 接收时间戳（Master 时间）

公式：

<meanPathDelay> = [(t2 - t1) + (t4 - t3)] / 2
                = [(t2 - t3) + (t4 - t1)] / 2

一步式 Sync：

<offsetFromMaster> = t2 - originTimestamp - <meanPathDelay> - <correctedSyncCorrectionField>

两步式 Sync：

<offsetFromMaster> = t2 - preciseOriginTimestamp - <meanPathDelay>
                     - <correctedSyncCorrectionField> - correctionField(Follow_Up)

其中 <correctedSyncCorrectionField> = correctionField(Sync) + ingress delayAsymmetry

Delay_Resp 计算（无 Follow_Up）：

<meanPathDelay> = [(t2 - t3) + (receiveTimestamp(Delay_Resp) - originTimestamp(Sync))
                   - <correctedSyncCorrectionField> - correctionField(Delay_Resp)] / 2

Delay_Resp 计算（有 Follow_Up）：

<meanPathDelay> = [(t2 - t3) + (receiveTimestamp(Delay_Resp) - preciseOriginTimestamp(Follow_Up))
                   - <correctedSyncCorrectionField> - correctionField(Follow_Up)
                   - correctionField(Delay_Resp)] / 2

7.2 Peer Delay (P2P) (Clause 11.4)

消息：Pdelay_Req, Pdelay_Resp, (Pdelay_Resp_Follow_Up)

时间戳：

  • t1 = Pdelay_Req 发送时间戳（Requester 时间）
  • t2 = Pdelay_Req 接收时间戳（Responder 时间）
  • t3 = Pdelay_Resp 发送时间戳（Responder 时间）
  • t4 = Pdelay_Resp 接收时间戳（Requester 时间）

一步式 Responder

  • Responder 设置 requestReceiptTimestamp = 0
  • Responder 计算周转时间 t3 - t2 并加到 Pdelay_Resp 的 correctionField

两步式 Responder（选项 A）

  • Responder 设置 requestReceiptTimestamp = 0
  • Pdelay_Resp_Follow_Up：responseOriginTimestamp = 0，correctionField += (t3 - t2)

两步式 Responder（选项 B）

  • Responder 设置 requestReceiptTimestamp = t2（秒+纳秒），从 correctionField 减去分数纳秒
  • Pdelay_Resp_Follow_Up：responseOriginTimestamp = t3（秒+纳秒），将分数纳秒加到 correctionField

Requester 计算

一步式：

<meanLinkDelay> = [(t4 - t1) - <correctedPdelayRespCorrectionField>] / 2

两步式：

<meanLinkDelay> = [(t4 - t1) - (responseOriginTimestamp - requestReceiptTimestamp)
                   - <correctedPdelayRespCorrectionField>
                   - correctionField(Pdelay_Resp_Follow_Up)] / 2

8. 透明时钟操作 (Clause 10)

8.1 驻留时间计算

<residenceTime> = <egressTimestamp> - <ingressTimestamp>

8.2 E2E TC — Sync 消息处理

一步式出口端口：

correctionField(Sync_egress) = correctionField(Sync_ingress)
                               + <residenceTime> + ingress<delayAsymmetry>

两步式出口端口（入口 Sync twoStepFlag = FALSE）：

  • 在出口 Sync 上设置 twoStepFlag = TRUE
  • 生成 Follow_Up：
    • preciseOriginTimestamp = originTimestamp(入口 Sync)
    • correctionField(Follow_Up) = <residenceTime> + ingress<delayAsymmetry>

两步式出口端口（入口 Sync twoStepFlag = TRUE）：

  • 不变地转发 Sync
  • correctionField(Follow_Up_egress) = correctionField(Follow_Up_ingress) + <residenceTime> + ingress<delayAsymmetry>

8.3 E2E TC — Delay_Req 消息处理

一步式：

correctionField(Delay_Req_egress) = correctionField(Delay_Req_ingress)
                                    + <residenceTime> - egress<delayAsymmetry>

两步式：

  • 不变地转发 Delay_Req
  • correctionField(Delay_Resp_egress) = correctionField(Delay_Resp_ingress) + <residenceTime> - egress<delayAsymmetry>

8.4 P2P TC — Sync 消息处理

一步式出口端口：

correctionField(Sync_egress) = correctionField(Sync_ingress)
                               + <residenceTime> + <meanLinkDelay> + ingress<delayAsymmetry>

两步式出口端口（入口 Sync twoStepFlag = FALSE）：

  • 设置 twoStepFlag = TRUE
  • Follow_Up correctionField = <residenceTime> + <meanLinkDelay> + ingress<delayAsymmetry>

两步式出口端口（入口 Sync twoStepFlag = TRUE）：

  • Follow_Up correctionField += <residenceTime> + <meanLinkDelay> + ingress<delayAsymmetry>

8.5 TC 中的 Pdelay_Resp_Follow_Up

对于两步式 Pdelay_Resp 的 E2E TC：

  • 若入口 twoStepFlag = FALSE → 设为 TRUE，生成 Pdelay_Resp_Follow_Up
  • correctionField(Pdelay_Resp_Follow_Up) = residenceTime(Pdelay_Resp) + residenceTime(Pdelay_Req)
  • responseOriginTimestamp = 0

RTL 设计提示：TC 的 correctionField 累加

  • correctionField 是 64-bit 有符号整数，单位 ns × 2¹⁶
  • 累加操作需处理溢出：全 1（除符号位）表示"过大"
  • residenceTime 由 egressTimestamp - ingressTimestamp 计算，通常 10–1000 ns 量级
  • P2P TC 需要每端口维护 meanLinkDelay 值（通过 Pdelay 机制测量）
  • 建议用 96-bit 或更宽内部累加器避免中间溢出

Correction field arithmetic64-bit 有符号整数，单位 = ns × 2¹⁶（亚纳秒在低 16 位）

E2E TC计算 residenceTime = egressTimestamp - ingressTimestamp；加到 correctionField
