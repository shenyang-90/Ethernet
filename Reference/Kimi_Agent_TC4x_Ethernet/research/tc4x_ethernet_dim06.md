## 1. MACsec (Media Access Control Security)

### 1.1 IEEE 802.1AE Standard Overview

MACsec (Media Access Control Security), defined in IEEE 802.1AE, is a Layer 2 security standard that provides connectionless data confidentiality, integrity, and origin authenticity for Ethernet frames [^286^][^263^]. Unlike IPsec (Layer 3) or TLS (Layer 4), MACsec operates at the Data Link Layer, securing all traffic above the Ethernet header transparently to upper-layer protocols.

**Key security services provided by MACsec:**
- **Confidentiality**: Encrypts the payload of Ethernet frames using AES-GCM [^260^]
- **Integrity**: Ensures frames have not been tampered with through ICV verification
- **Replay protection**: Prevents attackers from capturing and reusing frames via packet number (PN) tracking [^266^]
- **Origin authentication**: Verifies the frame came from a legitimate source within the secure association

The AURIX TC4x supports **accelerated MACsec via hardware accelerator in CSS (Cyber Security Satellite) and an application software driver** [^20^][^5^]. This is a significant advancement over TC3x, which had no dedicated MACsec hardware acceleration.

> **Key TC4x MACsec Support Statement:**
> "Accelerated MACsec support by HW accelerator in CSS and application SW driver" [^20^]

The TC4x's CSS module supports security algorithms for MACsec, IPsec, D/TLS, and SecOC (PDU level), providing dedicated hardware acceleration for automotive network security [^5^].

### 1.2 MACsec Frame Format (SecTAG + Encrypted Payload + ICV)

A MACsec-protected frame modifies the standard Ethernet frame by inserting a **MACsec Security Tag (SecTAG)** after the Ethernet header and appending an **Integrity Check Value (ICV)** at the end of the frame [^263^][^266^].

#### MACsec Frame Structure:

| Field | Size | Description |
|-------|------|-------------|
| Destination MAC | 6 bytes | Destination address (unencrypted) |
| Source MAC | 6 bytes | Source address (unencrypted) |
| **SecTAG** | **8-16 bytes** | **Security tag with key identifiers** |
| Encrypted Data | Variable | Original payload (encrypted) |
| **ICV** | **8-16 bytes** | **Integrity Check Value** |

**Total overhead: 32 bytes** (16 bytes SecTAG + 16 bytes ICV) [^261^]

#### SecTAG Field Details (16 bytes typical):

| Sub-field | Size | Description |
|-----------|------|-------------|
| MACsec EtherType | 2 bytes | Fixed value 0x88E5 - identifies MACsec frame [^263^] |
| TCI/AN | 1 byte | Tag Control Information (TCI) + Association Number (AN) |
| SL | 1 byte | Short Length field (6 bits + 2 reserved bits) [^266^] |
| PN | 4 bytes | Packet Number - used for replay protection and IV construction |
| SCI | 8 bytes | Secure Channel Identifier (MAC address + 16-bit port ID) [^263^] |

**TCI (Tag Control Information) bits include:**
- V: Version number
- ES: End Station bit
- SC: SCI present indicator
- SCB: Single Copy Broadcast
- E: Encrypted payload indicator
- C: Changed Text indicator
- AN: Association Number (2 bits) [^266^][^290^]

> "MACsec EtherType is 0x88e5 to indicate that the following frame is a MACsec frame" [^263^]

### 1.3 Security Associations and Key Management

#### MACsec Key Hierarchy

MACsec uses a hierarchical key structure managed by the **MACsec Key Agreement (MKA) protocol** defined in IEEE 802.1X [^287^][^288^]:

```
CAK (Connectivity Association Key)
  - Pre-shared key or derived from 802.1X EAP session
  |
  +-- KEK (Key Encrypting Key) -- encrypts SAK distribution
  |
  +-- ICK (Integrity Check Key) -- authenticates MKA messages
  |
  SAK (Secure Association Key)
    - Generated by Key Server (peer with lowest SCI)
    - Distributed to all peers encrypted with KEK
    - Used for actual data encryption (AES-128-GCM or AES-256-GCM)
```

**Key Management Flow:**

1. **Peer discovery** - MKA peers exchange EAPoL-MKA frames [^287^]
2. **CAK derivation** - From 802.1X EAP-TLS session keys or pre-shared key
3. **Key Server election** - Peer with lowest SCI becomes Key Server
4. **SAK generation** - Key Server generates SAK and distributes it encrypted with KEK
5. **Data encryption begins** - Both peers install SAK and start encrypting/decrypting
6. **SAK rotation** - Periodic key refresh for forward secrecy [^287^][^288^]

#### Automotive MACsec Profile

For automotive applications, the Open Alliance TC17 is defining a MACsec profile optimized for in-vehicle networks [^290^]:
- **Pre-shared CAK** (no EAP required) - CAK provisioned during production/service
- **Point-to-point MACsec** only (switched Ethernet)
- **Integrity-only** and **Integrity + Confidentiality** modes
- **Optimized MKA targeting <10ms startup** (vs. 3-8 seconds in traditional networks)
- Keys stored in HSM/CSRM for security [^290^]

### 1.4 Hardware Acceleration via CSS vs Software Implementation

The TC4x CSS (Cyber Security Satellite) provides dedicated hardware accelerators for MACsec operations, delivering significant performance improvements over pure software implementations [^5^][^21^].

#### CSS Hardware Accelerators for MACsec:

| Accelerator | Supported Modes | Performance @ 400MHz |
|-------------|-----------------|---------------------|
| AES-256 | CMAC-128 | 555 MB/s |
| AES-256 | CMAC-256 | 407 MB/s |
| AES-256 | GMAC-128 | 763 MB/s |
| AES-256 | GMAC-256 | 763 MB/s |

**Latency for Ethernet frames:**
- 64-byte frame: 0.135 us (128-bit key) / 0.155 us (256-bit key)
- 1024-byte frame: 1.335 us (128-bit key) / 1.355 us (256-bit key) [^21^]

> "Multiple HW accelerators to increase throughput, avoiding performance bottlenecks" [^21^]

**CSS Key Capabilities:**
- Up to **20+1 independent channels** for symmetric cryptography and hash functions (compared to 1 channel in TC3x) [^21^][^5^]
- **3x AES, Chacha20, SipHash, Poly1305, and SHAx** hardware accelerators
- **8KB internal RAM** for secret key storage (128, 192, 256-bit keys with attributes and IVs)
- **ASIL-D Safe MAC Comparator** for MAC verification (1 to 512 bits)
- Located on SRI crossbar with 2 CPUs and DMA for lowest latency [^21^]

#### Why Hardware Acceleration Matters for MACsec:

| Implementation | Throughput | CPU Load |
|---------------|------------|----------|
| Hardware offload (CSS) | Line-rate (up to 5 Gbps for GETH) | Minimal |
| Software encryption | 20-50% throughput reduction | Significant [^260^] |

> "Minimize latency & maximize throughput as an increasing number of security use cases are expected for the future" [^5^]

### 1.5 GETH MACsec Offloading Capabilities

The TC4x GETH module **does not have native built-in MACsec offloading** in the MAC itself. Instead, MACsec is implemented through a **combination of CSS hardware acceleration + software driver** [^20^][^5^].

**MACsec Data Path in TC4x:**

```
Ingress: PHY -> HSPHY -> XGMAC -> DMA -> CPU/CSS (decrypt/verify via CSS) -> Application
Egress:  Application -> CPU/CSS (encrypt/sign via CSS) -> DMA -> XGMAC -> HSPHY -> PHY
```

This is an **accelerated software implementation** rather than a fully offloaded MACsec engine:
- The CSS hardware performs the cryptographic operations (AES-GCM encryption/decryption, ICV generation/verification)
- The software driver handles SecTAG insertion/extraction, SCI management, PN tracking, and SA lookups
- The GETH MAC provides packet classification and filtering to support MACsec frame handling

> "Accelerated MACsec support by HW accelerator in CSS and application SW driver" [^20^]

## 2. Hardware Security in GETH

### 2.1 Packet Classification Rules

The TC4x GETH module provides flexible and programmable packet header inspection for **filtering, monitoring schemes, and enabling firewall protection and intrusion detection services** [^77^][^28^].

Key classification capabilities:
- **Traffic classification** between host port and ingress/egress ports [^77^]
- **Flexible Frame Parser (FFP)** for programmable packet inspection
- Support for **8 Gateway IDs** for stream-to-queue mapping [^33^]
- Classification based on multiple header fields (L2, L3, L4)

### 2.2 MAC Address Filtering (Unicast, Multicast, Hash Filter)

The XGMAC in TC4x includes a sophisticated **Address Filtering Module (AFM)** that checks the destination and/or source MAC addresses of all received frames [^28^][^78^].

#### Address Filtering Features:

| Feature | Specification |
|---------|--------------|
| DA Perfect Match Filters | Up to 32 destination address filters with per-byte masks [^78^] |
| SA Perfect Match Filters | Up to 31 source address filters with per-byte masks [^78^] |
| Hash Filter | 64-bit hash filter for multicast and unicast DAs [^78^] |
| Promiscuous Mode | Pass all frames without filtering (for monitoring) [^133^] |
| Pass All Multicast | Option to pass all multicast-addressed frames [^78^] |

**How AFM Works:**
> "The Address Filtering Module (AFM) checks the destination and/or source MAC addresses of all received frames and reports the address filtering status to the RFC. It also performs precise VLAN filtering and VLAN-based hash calculation for VLAN frames." [^28^]

> "Note: AFM itself does not directly filter received frames, but reports address filtering status to the RFC module (whether to drop the frame), and also indicates whether the received frame is multicast or broadcast." [^28^]

**Filter Types:**
- **Perfect filtering**: Exact match against programmed MAC addresses
- **Hash filtering**: CRC-based hash for scalable multicast/unicast filtering with possible false positives [^248^]
- **Inverse filtering**: Can be configured to reject matching addresses instead of accepting

### 2.3 VLAN Filtering

The TC4x GETH XGMAC supports comprehensive VLAN filtering capabilities:

| Feature | Description |
|---------|-------------|
| VLAN Perfect Match | Up to 32 VLAN-based perfect match filters [^78^] |
| VLAN Hash Filtering | Hash-based VLAN tag filtering [^78^] |
| Stacked VLAN | Support for up to two stacked VLAN tags (QinQ) [^79^] |
| VLAN Detection | VLAN-tagged frame detection, stripping, and filtering [^78^] |
| VLAN Inclusion | Per-frame VLAN tag inclusion via CSR |
| VLAN Tag Stripping | Option to strip up to two VLAN tags [^133^] |

**VLAN Filter Registers (from Linux XGMAC driver):**
- `XGMAC_VLAN_TAG` (0x00000050)
- `XGMAC_FILTER_VTFE` - VLAN Tag Filter Enable
- `XGMAC_VLAN_VTHM` - VLAN Tag Hash Match
- `XGMAC_VLAN_HASH_TABLE` (0x00000058) [^271^]

**Known Issue:** GETH_AI.015: "MAC Receive VLAN Tag Hash Filter Always Operates in Default Mode" - Workaround: disable VLAN hash filtering and use perfect/inverse filtering or software filtering [^247^].

### 2.4 Source Address Validation

The XGMAC supports **Source Address (SA) validation** for received frames:

- **SA Perfect Match**: Up to 31 source address filters with per-byte masks [^78^]
- SA comparison check with masking capability [^133^]
- Source address validation results reported in receive descriptor status
- Can be combined with destination address filtering for comprehensive access control

> "Up to 31 48-bit SA address comparison check with masks for each byte" [^133^]

### 2.5 L3/L4 Filtering Capabilities

The TC4x XGMAC provides advanced **Layer 3 and Layer 4 filtering**:

| Feature | Specification |
|---------|--------------|
| L3/L4 Match Filters | Up to 16 Layer 3 and Layer 4-based filters [^78^][^28^] |
| Protocol Support | TCP or UDP over IPv4 or IPv6 |
| L3 Matching | Source/destination IP address matching |
| L4 Matching | Source/destination port matching |
| Filter Types | Perfect match filters |

> "XGMAC receive packet filtering mechanism includes three core functions: the Address Filtering Module (AFM) checks the source and destination addresses of each input frame; supports extended filtering based on multiple VLAN tags and VLAN hash filtering; provides network layer (source/destination IP addresses) and transport layer (source/destination ports) two-level matching filter." [^28^]

**Additional Checksum Offload Features:**
- IPv4 header checksum offload on reception
- TCP, UDP, or ICMP checksum offload for received packets (IPv4 and IPv6) [^79^]
- Optional Layer 3/Layer 4 checksum offload module [^133^]

## 3. Intrusion Detection

### 3.1 GETH IDS Features

The TC4x GETH module supports **intrusion detection capabilities** through its flexible frame parsing and filtering infrastructure [^5^][^77^].

**Key IDS-related Features:**

> "Intrusion detection: supports detection of anomalies" [^5^]

> "Flexible/programmable packet header inspection for filtering, monitoring schemes and enable firewall protection and intrusion detection service" [^77^]

**IDS Capabilities:**
- **Programmable packet header inspection** - Flexible Frame Parser (FFP) enables deep packet inspection for anomaly detection
- **Traffic classification and monitoring** - Queue-based traffic observation for pattern analysis
- **MAC-level anomaly detection** - Detection of unusual frame patterns, sizes, or rates
- **Integration with SMU** - Security alarms can be routed to the Safety Management Unit for system-wide response [^28^][^82^]

### 3.2 Anomaly Detection Capabilities

The GETH module can detect various anomalies through its filtering and monitoring infrastructure:

| Anomaly Type | Detection Mechanism |
|-------------|-------------------|
| Invalid MAC addresses | AFM filtering rejects frames with non-matching addresses |
| VLAN tag anomalies | VLAN filtering detects unexpected VLAN IDs |
| L3/L4 protocol anomalies | L3/L4 filters detect unexpected protocols or ports |
| Frame size violations | Jabber timer detects oversized frames; padding detects undersized frames |
| CRC/FCS errors | Automatic CRC checking on receive [^79^] |
| Unexpected frame rates | MTL queue monitoring and DMA status tracking |
| Watchdog timeouts | Programmable receive watchdog timeout [^133^] |

**TSN Security Features (Anomaly Prevention):**

The **IEEE 802.1Qci Per-Stream Filtering and Policing (PSFP)** mechanism in TC4x provides DDoS protection:

> "802.1Qci isolates network fault effects or malicious attack interference to specific areas of the network. It is also called Ingress Policing, working at the switch ingress, filtering and managing each traffic flow... Qci specifically targets DDoS-like network attacks." [^33^]

PSFP Components:
1. **Stream Filter** (via FFP) - Identifies stream ID and maps to 1 of 8 gateway IDs
2. **Stream Gate** (via GCL) - Controls per-stream forwarding based on gate control list
3. **Flow Meter** (via PC) - Polices stream bandwidth to prevent flooding [^33^]

### 3.3 Event Reporting to SMU

The TC4x GETH module can report security-relevant events to the **Safety and Security Alarm Management Unit (SMU)** [^82^][^83^].

**SMU Architecture for Security:**

```
GETH Security Events -> SMU_CS (Security Alarm Handler)
  -> Configurable reactions: NMI, Interrupt, Reset, FSP
```

**SMU Security Alarm Handler (SMU_CS):**
- Each security alarm can be individually configured to trigger specific reactions [^83^]
- Independent access protection mechanism to protect SMU_CS configuration [^83^]
- Reactions include: NMI to CPUs, interrupt requests, application/system reset, Fault Signaling Protocol (FSP) [^82^]

**Security Use Cases Covered:**

> "In-vehicle network (I/N) & V2x security: Intrusion Detection System (IDS), Intrusion Detection Prevention System (IDPS)" [^5^]

> "E/E COM(message) observation: Intrusion Detection System (IDS); E/E COM(message) filtering: Intrusion Detection Prevention System (IDPS)" [^5^]

**Note:** The GETH module connects to both the IR (Interrupt Router) and SMU modules for event reporting [^28^]. Security alarms from GETH are processed by the SMU_CS security alarm handler.

## 4. Firewall Capabilities

### 4.1 Hardware Filter Rules in MAC

The TC4x GETH provides extensive **hardware-based filtering** that can be used to implement firewall functionality:

> "Firewall: feasible with hardware filters in MAC and software" [^5^][^262^]

**Hardware Filter Summary:**

| Filter Type | Count | Match Type |
|-------------|-------|------------|
| DA Perfect Match | Up to 32 | Full 48-bit MAC with byte mask |
| SA Perfect Match | Up to 31 | Full 48-bit MAC with byte mask |
| DA/SA Hash | 64-bit | CRC-based hash filter |
| VLAN Perfect Match | Up to 32 | VLAN ID |
| VLAN Hash | Optional | Hash-based VLAN filtering |
| L3/L4 Filters | Up to 16 | IP address + TCP/UDP port |

**Filtering Process Flow:**
1. AFM checks destination and source MAC addresses
2. VLAN tag filtering (perfect or hash match)
3. L3/L4 filtering (IP addresses, protocol, ports)
4. Results combined to determine pass/drop decision
5. Frame passed to appropriate DMA queue or dropped [^28^]

### 4.2 Software Firewall Implementation

Beyond hardware filters, the TC4x enables **software-based firewall** implementations:

- Flexible Frame Parser (FFP) can identify traffic flows for software processing
- Receive descriptors include comprehensive filter status for software decision-making
- Software can implement stateful firewall logic above the hardware filtering layer
- Combined with CSS for authenticated firewall rules (cryptographic verification)

> "Firewall: feasible with HW filters in MAC and SW" [^5^]

### 4.3 Rate Limiting

The TC4x GETH implements rate limiting through the **IEEE 802.1Qci Per-Stream Filtering and Policing (PSFP)** mechanism:

#### Police Counter (PC) - Traffic Metering:

> "Traffic meter: implemented through the PC (Police Counter) in the AURIX TC4x GETH MAC, the PC is selected through the PCV/PCN file in the frame parsing command" [^29^]

**PSFP Rate Limiting Components:**

1. **Stream Filter** (FFP-based):
   - Identifies flow ID and maps to 1 of 8 gateway IDs
   - Only 8 gateway IDs supported [^33^]

2. **Stream Gate** (GCL-based):
   - Controls per-stream forwarding using Gate Control List entries
   - Time-gated transmission for scheduled traffic

3. **Police Counter (PC)**:
   - Implements token bucket-based metering
   - Protects TSN from traffic anomalies or faulty nodes [^33^]
   - Enforces bandwidth limits per stream

> "The flow meter is implemented through the PC (Police Counter) in the AURIX TC4x GETH MAC... protecting TSN from anomalies such as attacks, traffic anomalies, or failures of terminal stations or other bridges" [^33^]

**Additional Rate Control Features:**
- **IEEE 802.3x Flow Control**: Automatic PAUSE frame generation
- **Priority-based Flow Control (PFC)**: IEEE 802.1Qbb per-priority PAUSE [^78^]
- **MTL Queue Thresholds**: Programmable Rx queue thresholds for backpressure
- **Watchdog Timer**: Programmable receive watchdog timeout [^133^]

## 5. CSS Integration: How CSS Accelerators Work with GETH for MACsec

### 5.1 CSS Architecture Overview

The **Cyber Security Satellite (CSS)** is a novel addition to the TC4x security cluster, designed for parallel cryptographic acceleration to serve the application area [^21^][^262^].

**CSS Key Characteristics:**

> "Brand new module located on SRI. Up to 20+1 channels for independent task for symmetric cryptography and Hash functions. 3 x AES, Chacha20, SipHash(2-4,4-8), Poly1305 and SHAx HW accelerators" [^21^]

**CSS Integration in TC4x:**

```
Cybersecurity Domain:
  TriCore(s) + DMA + D-NVMcs + RNG + PKC
         |
      SRI Interconnect
         |
    +----+----+
    |         |
  CSS      CSRM (Cyber Security Real-time Module)
    |         |
  SRI Bus -- Bridge -- NVMcs
    |
  20+1 Channels -> AES/GHASH/SHA/SipHash/Chacha20/Poly1305
```

### 5.2 CSS-GETH Interaction for MACsec

The TC4x implements MACsec through a **CSS-accelerated software architecture** rather than inline MACsec offloading:

#### Data Flow for MACsec Operations:

**Egress (TX) Path:**
1. Application provides plaintext Ethernet frame to network stack
2. MACsec driver prepares frame: adds SecTAG header (EtherType 0x88E5, SCI, PN)
3. CSS accelerator performs **AES-GCM encryption** on payload + generates **ICV**
4. Complete MACsec frame sent to GETH DMA for transmission
5. GETH XGMAC adds preamble, SFD, CRC and transmits via PHY

**Ingress (RX) Path:**
1. GETH XGMAC receives frame from PHY
2. Frame filtering checks if frame is MACsec (EtherType 0x88E5)
3. MACsec frame delivered to MACsec driver via DMA
4. CSS accelerator performs **AES-GCM decryption** + **ICV verification**
5. If ICV valid, plaintext frame passed to network stack; if invalid, frame dropped

#### CSS Cryptographic Engines for MACsec:

| Engine | MACsec Use | Performance |
|--------|-----------|-------------|
| AES-256 HW x3 | AES-GCM-128/256 encryption/decryption | Up to 763 MB/s (GMAC) |
| GHASH | Galois Hash for GCM mode | Integrated with AES |
| SHA-2/SHA-3 | Key derivation functions | 356-2492 MB/s |
| SipHash | Optional MAC algorithms | 640-1280 MB/s |

#### Key Management Integration:
- CSS provides secure key storage in 8KB internal RAM
- Keys (SAK, KEK, ICK) stored with attributes and IVs
- CSRM manages key lifecycle and access rights
- **No read interface to CSS RAM** - keys cannot be extracted [^21^]

**CSS Performance at 400 MHz:**

| Mode | MB/20ms | ms/12MB | ms/24MB | MB/s |
|------|---------|---------|---------|------|
| CMAC-128 | 11.1 | 21.6 | 43.2 | 555 |
| CMAC-256 | 8.14 | 29.5 | 59 | 407 |
| GMAC-128 | 15.3 | 15.7 | 31.4 | 763 |
| GMAC-256 | 15.3 | 15.7 | 31.4 | 763 |

**Hash Function Performance:**

| Mode | Cycles/Bytes | MB/s @ 400MHz |
|------|-------------|---------------|
| SHA1 | 88/64B | 292 |
| SHA2-256 | 72/64B | 356 |

[^21^]

### 5.3 Freedom of Interference via CSS Channels

One of the key advantages of the CSS architecture for MACsec is **freedom of interference** between different security domains:

> "Parallelization of HW accelerators in service provider to application area to avoid performance bottlenecks by: Increasing throughput, Minimizing latency, 21 individual channels to be used by application (compared to one channel in TC3x), Providing freedom of interference for domain/zone controllers" [^5^]

**Channel Allocation:**
- Each MACsec session or security context can use a dedicated CSS channel
- Channel access rights configured by CSRM for isolation
- Independent priority, interrupt mapping, and alarm thresholds per channel
- Channels can be allocated to different VMs for virtualized MACsec [^21^]

### 5.4 Security Alarm Integration

Failed MACsec authentication operations can generate security alarms:

- CSS ASIL-D MAC comparator detects authentication failures [^21^]
- Per-channel threshold for failed authentication generating alarm [^21^]
- Alarms routed to SMU_CS for configurable system response (NMI, reset, FSP)
- Key locking on security events to prevent further use of compromised keys [^21^]
