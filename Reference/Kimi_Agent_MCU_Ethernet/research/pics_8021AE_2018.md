# IEEE Std 802.1AE-2018 (MACsec) 协议分析与PICS提取

> **协议名称**: IEEE Std 802.1AE-2018 — IEEE Standard for Local and Metropolitan Area Networks: Media Access Control (MAC) Security  
> **分析日期**: 2025年  
> **分析焦点**: 车载以太网区域控制器 (Zonal Controller) 应用  

---

## 一、协议概述

### 1.1 协议范围与目的

IEEE Std 802.1AE-2018 定义了 **MAC Security (MACsec)** 协议，为IEEE 802局域网提供的MAC Service提供透明的安全保护。MACsec在数据链路层（Layer 2）运行，对上层协议完全透明，能够在不需要修改现有网络协议栈的情况下实现安全通信。

**核心安全服务**:
- **无连接用户数据机密性 (Connectionless user data confidentiality)**: 通过加密算法保护用户数据
- **帧数据完整性 (Frame data integrity)**: 确保帧内容未被篡改
- **数据源真实性 (Data origin authenticity)**: 验证帧的来源身份
- **重放保护 (Replay protection)**: 防止恶意重放历史帧

MACsec最初于2006年发布（IEEE Std 802.1AE-2006），2018版整合了以下修订：
- IEEE Std 802.1AEbn-2011: 增加 GCM-AES-256 加密套件
- IEEE Std 802.1AEbw-2013: 增加 GCM-AES-XPN-128/256 扩展包序号加密套件
- IEEE Std 802.1AEcg-2017: 定义Ethernet Data Encryption devices (EDEs)

### 1.2 核心组件

#### 1.2.1 SecY (MAC Security Entity)

SecY是MACsec的核心功能实体，每个SecY通过**Common Port**使用MAC Service，向其**Controlled Port**的用户提供安全MAC Service实例，向其**Uncontrolled Port**的用户提供非安全服务实例。

**SecY架构包含三个端口**:
- **Controlled Port (受控端口)**: 提供安全的MAC Service，所有帧经过加密/完整性保护
- **Uncontrolled Port (非受控端口)**: 提供非安全的透明传输，用于密钥协商协议(如MKA)
- **Common Port (公共端口)**: 连接到下层物理网络

**SecY功能组件**:
- **Secure Frame Generation (安全帧生成, 10.5)**: 对发送帧进行加密和完整性保护
- **Secure Frame Verification (安全帧验证, 10.6)**: 对接收帧进行验证和解密
- **Cipher Suite(s) (加密套件)**: 提供PROTECT和VALIDATE操作
- **Key Agreement Entity (KaY) 接口**: 通过Layer Management Interface (LMI)与密钥协商实体通信

#### 1.2.2 SAK (Secure Association Key) 与 SC (Secure Channel)

**Secure Channel (SC, 安全信道)**:
- SC是单向安全通信信道，由**SCI (Secure Channel Identifier)** 唯一标识
- SCI = 48-bit MAC Address + 16-bit Port Identifier (共64位)
- 每个SecY至少支持1个接收SC和1个发送SC

**Secure Association (SA, 安全关联)**:
- SA是SC内的具体安全会话，由**AN (Association Number, 2-bit)** 标识
- 每个SC可包含最多4个SA (AN = 0, 1, 2, 3)
- 每个SA使用一个**SAK (Secure Association Key)**

**Secure Association Key (SAK)**:
- 用于Cipher Suite的对称密钥
- GCM-AES-128/XPN-128: 128位密钥
- GCM-AES-256/XPN-256: 256位密钥
- 通过MKA (MACsec Key Agreement) 协议协商分发

#### 1.2.3 MACsec帧格式

MACsec帧在原始以太网帧基础上增加两个字段：**SecTAG** 和 **ICV**。

**帧结构**:
```
| Destination MAC (6B) | Source MAC (6B) | SecTAG (8/16B) | Secure Data | ICV (8-16B) |
```

**SecTAG 结构** (Clause 9):
| 字段 | 长度 | 说明 |
|------|------|------|
| MACsec EtherType | 2 octets | 0x88E5，标识MACsec帧 |
| TCI (TAG Control Information) | 1 octet | 版本、控制标志 |
| AN (Association Number) | 4 bits | SA标识 (0-3) |
| SL (Short Length) | 1 octet | 短帧长度指示 |
| PN (Packet Number) | 4 octets | 包序号 (低32位) |
| SCI (可选) | 8 octets | 安全信道标识符 |

**TCI 标志位**:
- **V (Version)**: 协议版本，当前为0
- **ES (End Station)**: 使用源MAC地址推导SCI
- **SC (SC present)**: SCI显式包含在SecTAG中
- **SCB (Single Copy Broadcast)**: EPON单拷贝广播
- **E (Encryption)**: 机密性保护启用
- **C (Changed)**: 用户数据被修改/ICV非16字节

**ICV (Integrity Check Value)**:
- 由Cipher Suite生成的完整性校验值
- GCM-AES系列: 128位 (16 octets)

#### 1.2.4 加密算法 (Cipher Suites)

| Cipher Suite | 标识符 | 算法 | 密钥长度 | PN长度 | 完整性 | 机密性 | 状态 |
|-------------|--------|------|----------|--------|--------|--------|------|
| GCM-AES-128 | 00-80-C2-00-01-00-00-01 | AES-GCM | 128位 | 32位 | 是 | 是 | **必选** |
| GCM-AES-256 | 00-80-C2-00-01-00-00-02 | AES-GCM | 256位 | 32位 | 是 | 是 | 可选 |
| GCM-AES-XPN-128 | 00-80-C2-00-01-00-00-03 | AES-GCM | 128位 | 64位 | 是 | 是 | 可选 |
| GCM-AES-XPN-256 | 00-80-C2-00-01-00-00-04 | AES-GCM | 256位 | 64位 | 是 | 是 | 可选 |

**Default Cipher Suite = GCM-AES-128** (Clause 14.5):
- 使用NIST SP 800-38D指定的Galois/Counter Mode
- IV = SCI(64-bit) + PN(32-bit)
- ICV长度 = 128位
- 支持完整性保护（无加密）和机密性保护两种模式

**XPN (Extended Packet Number) 套件特点**:
- 使用64位PN（而非32位），可保护超过2^32帧而不需更换SAK
- 引入Salt(96-bit)和SSCI(32-bit)参数
- 适用于100Gb/s+高速网络
- **不支持confidentiality offset**

#### 1.2.5 密钥协商: 802.1X/MKA

MACsec依赖于 **IEEE Std 802.1X-2010** 中定义的 **MKA (MACsec Key Agreement)** 协议进行密钥管理：

- **EAPOL (Extensible Authentication Protocol over LAN)**: 用于传输MKA消息
- **CA (Connectivity Association)**: 由MKA建立的安全连接关联
- **Key Server**: MKA选举出的密钥服务器负责分发SAK
- **SAK派生**: 基于MSK (Master Session Key) 派生
- **MKA Key Number (KN)**: 用于标识和排序SAK

**MKA关键功能**:
1. 对等体认证和授权
2. CA成员关系管理
3. Key Server选举
4. SAK生成、分发和安装
5. 存活检测 (Live Peer detection)
6. PN耗尽预警和SAK更换

### 1.3 车载网络应用分析

#### 1.3.1 为什么车载网络需要MACsec

现代汽车电子架构正从**域控制器 (Domain Controller)** 向**区域控制器 (Zonal Controller)** 演进，车载以太网成为骨干网络技术。MACsec在车载环境中的关键价值：

**防止中间人攻击 (Man-in-the-Middle Protection)**:
- 保护区域内通信链路（如以太网交换机到ECU之间）
- 防止恶意设备接入车载网络后窃听或篡改通信
- 数据完整性保护确保控制命令不被篡改

**保护关键控制数据 (Critical Data Protection)**:
- ADAS传感器数据（摄像头、雷达、激光雷达）
- 底盘控制信号（制动、转向、悬架）
- 动力系统控制数据
- OTA (Over-The-Air) 更新数据

**满足ISO 21434要求**:
- ISO/SAE 21434 (Road Vehicles — Cybersecurity Engineering) 要求车辆网络通信应具备适当的安全保护
- MACsec提供Layer 2级别的透明加密，符合 defence-in-depth 策略
- 支持ASIL相关安全关键数据的保护

#### 1.3.2 车载区域控制器中的MACsec部署

**典型部署场景**:
```
[传感器/执行器 ECU] ===(MACsec)=== [区域控制器 (Zonal Gateway)] ===(MACsec)=== [中央计算平台]
```

**区域控制器中的MACsec需求**:
- **硬件加速必需**: MACsec加密/解密需要高吞吐量，通常由硬件实现
- **低延迟要求**: 控制数据对延迟敏感，需要满足Table 10-3性能要求
- **密钥管理简化**: 车载环境可能使用预配置密钥（静态SAK）而非完整的MKA
- **多端口支持**: 区域控制器需要同时保护多个链路

**MCU实现考量**:
- **Infineon TC4x**: 内置CSS (Cyber Security Subsystem) 硬件加速器，支持763MB/s MACsec处理
- **NXP S32G**: 需外部MACsec PHY (如NXP TJA1103不支持MACsec)
- **Renesas R-Car**: MACsec支持信息未公开

## 四、车载区域控制器应用分析

### 4.1 区域控制器中MACsec的必要PICS项

对于车载区域控制器中的MACsec实现，以下PICS项目具有特殊重要性：

#### 4.1.1 必选功能 (M — 必须支持)

| 类别 | PICS项 | 区域控制器意义 |
|------|--------|---------------|
| 核心架构 | SAP, STAT, GEN, VER, FMT, SCI | 构成SecY的基本功能，必须全部实现 |
| 性能 | PERF | 必须满足Table 10-3延迟要求，确保控制数据实时性 |
| 密钥接口 | KAY-1~KAY-11 | 所有KAY LMI功能必须实现以支持MKA密钥协商 |
| 管理 | MGT1-1~MGT1-14, MGT4-1~MGT4-29 | 状态监控和统计计数对故障诊断至关重要 |
| 加密套件 | CS, CSI | 必须支持GCM-AES-128（完整性+可选机密性） |
| 安全帧处理 | GEN-1~GEN-15, VER-1~VER-14 | 完整的帧保护和验证流程 |

#### 4.1.2 强烈建议的可选功能 (Recommended Optional)

| PICS项 | 区域控制器意义 |
|--------|---------------|
| CSC | 支持无offset机密性保护 — 用于保护敏感控制数据 |
| CSA (GCM-AES-256) | 256位加密提供更高安全级别，满足未来安全要求 |
| MGT2-1~MGT2-7 | 运行时参数可配置能力 — 支持诊断和调试 |
| MSAK | 支持多于2个receive SAK — 支持无中断密钥切换 |

#### 4.1.3 车载环境中不太关键的功能

| PICS项 | 原因 |
|--------|------|
| CSO (confidentiality offset) | XPN套件不支持此功能；车载环境通常需要完全加密 |
| MIB (SNMPv3) | 车载网络通常不使用SNMP管理 |
| TC (多transmit SC) | 车载多为点对点链路，不需要多SC |
| MGT3-1~MGT3-5 (管理创建SA/SC/SAK) | 车载环境通常通过MKA自动管理密钥 |

### 4.2 硬件实现考量

#### 4.2.1 MACsec硬件加速的必要性

MACsec的GCM-AES操作计算密集，在车载区域控制器中**强烈建议硬件实现**：

- **GCM-AES操作**: 每个帧需要AES计数器模式加密 + GHASH认证标签计算
- **100Mbps~1Gbps车载以太网**: 软件实现难以满足吞吐量要求
- **Table 10-3延迟要求**: 硬件实现才能满足严格的SecY transmit/receive延迟
- **SAK切换延迟**: 硬件支持才能实现<64 octet线传输时间的无丢包切换

#### 4.2.2 主要车载MCU MACsec支持情况

| MCU平台 | MACsec支持 | 实现方式 | 吞吐量 | 区域控制器适用性 |
|---------|-----------|----------|--------|-----------------|
| Infineon TC4x (AURIX) | 是 | CSS (Cyber Security Subsystem) 硬件加速器 | 763 MB/s | **优秀** — 内置硬件加速 |
| NXP S32G | 否 (需外部PHY) | 需外部MACsec-capable PHY (如TJA1103不支持) | 取决于PHY | 有限 — 需额外硬件 |
| Renesas R-Car S4 | 未公开 | 信息未公开 | 未公开 | 不确定 |
| NXP S32N | 是 | 内置MACsec硬件 | 高 | **优秀** — 专为车载网络设计 |

### 4.3 密钥管理策略

#### 4.3.1 MKA (动态密钥协商)

**适用场景**: 车辆运行时动态建立安全连接

**优点**:
- 自动密钥分发和更新
- 支持PN耗尽前的预防性密钥更换
- 标准化互操作

**车载实现考量**:
- 需要802.1X PAE和EAPOL支持
- 增加启动时间和CPU开销
- 需要证书基础设施支持

#### 4.3.2 静态SAK (预配置密钥)

**适用场景**: 固定安全域内的简化部署

**优点**:
- 实现简单，无运行时密钥协商开销
- 确定性行为，适合安全关键系统
- 启动时间更快

**车载实现考量**:
- 密钥需安全存储 (HSM/TEE)
- 需要密钥轮换机制 (OTA更新)
- 适合传感器到区域控制器的固定链路

### 4.4 安全建议

#### 4.4.1 Cipher Suite选择建议

| 应用场景 | 推荐Cipher Suite | 原因 |
|----------|-----------------|------|
| 一般控制数据 | GCM-AES-128 | 满足当前安全要求，硬件支持广泛 |
| 高安全级别数据 (制动/转向) | GCM-AES-256 | 更高密钥强度，满足未来要求 |
| 高速数据流 (摄像头/雷达) | GCM-AES-XPN-128 | 64位PN避免高速下频繁密钥更换 |
| 最高安全高速数据 | GCM-AES-XPN-256 | 最高安全级别+大PN空间 |

#### 4.4.2 车载部署最佳实践

1. **所有车载以太网链路启用MACsec**: 包括ECU到交换机、交换机到交换机、区域到中央
2. **完整性+机密性双重保护**: 不仅防篡改还要防窃听
3. **Strict验证模式**: 丢弃所有验证失败帧
4. **启用重放保护**: 防止重放攻击
5. **HSM存储SAK**: 密钥安全存储在硬件安全模块
6. **定期SAK轮换**: 通过MKA或OTA实现周期性密钥更新
7. **监控MACsec统计计数器**: 检测异常流量模式
8. **与ISO 21434流程对齐**: MACsec部署纳入网络安全管理体系

## 五、总结

IEEE Std 802.1AE-2018为车载区域控制器提供了成熟、标准化的Layer 2安全解决方案。标准包含完整的PICS proforma (Annex A)，涵盖了从核心SecY功能到管理统计的完整功能集合。

**关键要点**:
1. **GCM-AES-128是必选Cipher Suite**，所有实现必须支持完整性保护
2. **SecY性能要求严格** (Table 10-3)，车载环境建议硬件加速实现
3. **MKA提供标准化密钥管理**，但车载环境可考虑静态SAK简化
4. **PICS提供了详细的实现检查清单**，可用于供应商评估和一致性测试
5. **MACsec与ISO 21434对齐**，满足车辆网络安全法规要求

对于车载区域控制器MCU选型，**优先选择内置MACsec硬件加速器的平台**（如Infineon TC4x CSS），以确保满足性能和延迟要求。
