# IEEE Std 802.1CB-2017 协议分析与PICS提取

## Frame Replication and Elimination for Reliability (FRER)

---

## 1. 协议概述分析

### 1.1 协议范围和目的

IEEE Std 802.1CB-2017 全称《IEEE Standard for Local and Metropolitan Area Networks — Frame Replication and Elimination for Reliability》，是IEEE 802.1工作组定义的Time-Sensitive Networking (TSN) 核心标准之一。该标准规定了网桥（Bridge）和端系统（End System）中用于提供数据包冗余传输识别、复制以及重复数据包识别和消除的程序、管理对象和协议。

FRER的核心目标是**显著降低数据包丢失概率**，通过将数据流（Stream）分成一个或多个链路化的成员流（Member Stream），构成复合流（Compound Stream），在发送端或中间中继节点复制数据包并通过多条独立路径传输，在接收端或汇聚节点根据序列号消除重复数据包，从而实现极高的传输可靠性。本标准**不涉及**多条冗余路径的创建机制，路径控制由其他标准（如IEEE 802.1Qca路径控制和枚举、IEEE 802.1Qcc TSN配置）负责。

### 1.2 FRER核心机制

#### 1.2.1 序列编号生成（Sequence Number Generation）

序列号生成功能（7.4.1节）为每个下传的数据包生成一个`sequence_number`子参数。序列号空间（GenSeqSpace）为65536（16位无符号整数），每个序列号生成实例独立维护一个`GenSeqNum`变量，每发送一个数据包后递增1，达到最大值后回绕至0。序列号生成通过`SequenceGenerationAlgorithm`例程实现，在`DATA_REQUEST`事件触发时执行，确保每个数据包都被赋予唯一连续的序列号标识。

#### 1.2.2 帧复制（Frame Replication）

帧复制通过**流分割功能（Stream Splitting Function, 7.7节）**实现。该功能接收上层传来的带`stream_handle`的数据包，生成零个或多个副本，每个副本可被赋予不同的`stream_handle`（即不同的Member Stream标识），从而将原始Compound Stream拆分为多个Member Stream。在Bridge中，帧复制也可通过标准的多播转发机制配合输出端口的Active Stream Identification功能实现（8.2节）。

#### 1.2.3 帧消除（Frame Elimination）

帧消除是FRER的核心功能，包含两层机制：

- **Individual Recovery Function（7.5节）**：基于Base Recovery Function（7.4.3节），作用于单个Member Stream，用于检测和消除来自卡死发送器（stuck transmitter）的重复帧。可配置使用`VectorRecoveryAlgorithm`或`MatchRecoveryAlgorithm`。
- **Sequence Recovery Function（7.4.2节）**：作用于Compound Stream的所有Member Stream，通过比较序列号消除来自多条路径的重复数据包。要求每个Listener和Relay系统至少支持`MatchRecoveryAlgorithm`，同时要求`VectorRecoveryAlgorithm`的`frerSeqRcvyHistoryLength >= 2`。

`VectorRecoveryAlgorithm`（7.4.3.4节）使用位图历史窗口（SequenceHistory）来跟踪已接收的序列号，适合处理Bulk Streams；`MatchRecoveryAlgorithm`（7.4.3.5节）仅保留最近接收的序列号，适合Intermittent Streams。

#### 1.2.4 序列恢复（Sequence Recovery）

序列恢复功能整合了Base Recovery Function和Latent Error Detection（7.4.4节）。**潜在错误检测**通过监控丢弃包数量与预期值的偏差来检测某条冗余路径是否发生静默故障（latent error）。当`frerSeqRcvyLatentErrorPaths > 1`且检测周期大于0时，系统定期执行`LatentErrorTest`算法，若实际丢弃包数与理论预期值之差超过阈值`frerSeqRcvyLatentErrorDifference`，则触发`SIGNAL_LATENT_ERROR`告警。

#### 1.2.5 序列编解码（Sequence Encode/Decode）

FRER定义了三种序列号编解码格式（7.6-7.10节）：
- **R-TAG（Redundancy Tag, 7.8节）**：6字节标签，包含2字节EtherType（0xF1C1）+ 2字节Reserved + 2字节Sequence Number，插入到帧的`mac_service_data_unit`起始位置。
- **HSR Sequence Tag（7.9节）**：兼容IEC 62439-3 HSR协议的16位序列号格式。
- **PRP Sequence Trailer（7.10节）**：兼容IEC 62439-3 PRP协议的序列号尾部格式。

### 1.3 与TSN其他协议的关系

| 协议标准 | 关系说明 |
|---------|---------|
| **IEEE 802.1Q-2014** | FRER基于802.1Q的Bridge架构，依赖EISS（Enhanced Internal Sublayer Service）和VLAN转发机制 |
| **IEEE 802.1Qcc** | TSN配置协议，负责FRER流配置的集中式或分布式管理（UNI接口） |
| **IEEE 802.1Qca** | 路径控制和枚举协议，负责创建和维护FRER所需的冗余传输路径 |
| **IEEE 802.1Qbv** | 增强流量整形（TAS），可与FRER配合实现零拥塞丢包 |
| **IEEE 802.1Qci** | 逐流过滤和监管（PSFP），与FRER的流识别功能协同工作 |
| **IEC 62439-3** | HSR/PRP协议互操作，FRER支持HSR和PRP序列号格式（Annex B） |

### 1.4 车载网络应用

FRER在车载网络中具有关键应用价值：

- **自动驾驶关键数据冗余传输**：对于ADAS/AD传感器数据（如摄像头、LiDAR、Radar）、底盘控制信号（转向、制动）等高安全等级数据流，FRER提供端到端的冗余传输保障，有效应对线缆故障、交换机端口故障等单点故障场景。
- **安全相关通信（ASIL等级要求）**：在ISO 26262功能安全框架下，FRER的潜在错误检测（Latent Error Detection）机制可用于满足ASIL-D等级对通信故障检测的要求。
- **Zonal Controller架构适配**：在区域控制器架构中，FRER可同时作为Talker（向上行链路发送冗余传感器数据）和Listener（接收来自其他区域控制器的冗余控制指令），Relay功能则可用于域间骨干网交换机的中间恢复节点。
- **低延迟要求**：FRER的帧消除操作仅涉及序列号比较，无需缓冲等待重排序，因此不会引入额外的端到端延迟。

### 2.1 PICS来源

本协议**已包含标准PICS proforma**，位于Annex A（第78-86页）。PICS proforma按照ISO/IEC 9646-1和ITU-T X.290系列规范编写，包含以下主要部分：
- A.2.1 Major capabilities/options（主要能力/选项）
- A.2.2 Stream identification component（流识别组件）

- A.2.4 Listener end system（Listener端系统）
- A.2.5 Relay system（中继系统）
- A.2.6 FRER 802.1Q C-component（C组件）
- A.2.7 Common requirements（通用要求）

| **M** | Mandatory（强制） |

## 4. 车载Zonal Controller应用分析

### 4.1 架构定位

在车载Zonal架构中，802.1CB FRER适用于以下场景：

```
                    [Central Compute]
                         |     |
                    (FRER Listener)  <- 冗余控制指令接收
                         |     |
                    =====|=====|=====  <- 骨干网冗余链路
                        /       \
                 [Zonal Ctrl A]  [Zonal Ctrl B]
                 (Talker+Listener) (Talker+Listener)
                 (Relay功能可选)    (Relay功能可选)
                    /    |    \
                 ECU1  ECU2  ECU3  <- 本地传感器/执行器
```

### 4.2 关键PICS项与车载MCU实现映射

| Infineon TC4x (软件) | Yes | Yes | Yes | 可选 | Match + Vector | R-TAG | 软件实现所有功能 |
| NXP S32G (混合) | Yes | Yes | Yes | Yes | Match + Vector | R-TAG + HSR | 硬件加速待确认 |

### 4.3 车载实现特别关注点

#### 4.3.1 Bridge端点的双重角色要求

车载Zonal Controller通常需要**同时支持Talker和Listener功能**：
- **Talker侧（TE9-TE13）**：为传感器数据流生成序列号、复制帧、分配Member Stream
- **Listener侧（LE2-LE6）**：接收来自中央计算单元或其他Zonal Controller的冗余数据流，执行序列恢复和重复帧消除
- 建议PICS中同时声明TE和LE为Yes

#### 4.3.2 序列恢复算法选择

| 算法 | 适用场景 | 车载推荐度 |
|------|---------|:---------:|
| MatchRecoveryAlgorithm | Intermittent Streams，低带宽控制信号 | ★★★★★ |
| VectorRecoveryAlgorithm | Bulk Streams，高带宽传感器数据 | ★★★★★ |

对于高带宽传感器数据（摄像头、LiDAR），**必须支持VectorRecoveryAlgorithm**（LE4/RS5要求`frerSeqRcvyHistoryLength >= 2`）。

#### 4.3.3 HSR/PRP兼容性

当车载网络需要与工业TSN设备或采用HSR/PRP协议的子系统互操作时：
- TE16/TE17/LE12/LE13 声明HSR/PRP支持
- 注意HSR使用每源MAC地址序列号（而非每Stream），需在配置中选择`per-source sequence numbering`

#### 4.3.4 Latent Error Detection（潜在错误检测）

**强烈建议**在车载安全应用中启用潜在错误检测（COM3-COM7）：
- `frerSeqRcvyLatentErrorPeriod`: 建议配置为1秒以内
- `frerSeqRcvyLatentErrorDifference`: 根据实际丢包容忍度配置
- 检测多条冗余路径中的一条路径静默故障，符合ASIL-D对通信故障检测的要求

#### 4.3.5 实现方式建议

| 功能 | 软件实现 | 硬件加速 |
|------|:-------:|:-------:|
| Sequence Generation | TC4x可行 | 推荐硬件offload |
| Sequence Recovery (Match) | TC4x可行 | 推荐硬件offload |
| Sequence Recovery (Vector) | TC4x可行（需优化） | **强烈建议硬件** |
| R-TAG Encode/Decode | 所有平台可行 | 可选 |
| Stream Identification | TC4x可行 | 可选 |
| Individual Recovery | TC4x可行 | 可选 |

## 5. 总结

IEEE 802.1CB-2017定义了FRER（Frame Replication and Elimination for Reliability）机制，是TSN协议族中保障高可靠传输的核心标准。本协议已包含完整的PICS proforma（Annex A），覆盖了五种设备类型（Stream Identification Component、Talker、Listener、Relay System、FRER C-component）的强制和可选功能要求。

对于车载Zonal Controller应用，重点关注的PICS项包括：
1. **TE9/TE10/TE13**（Talker序列生成、编解码、流分割）
2. **LE2-LE6**（Listener序列恢复和Individual Recovery）
3. **RS2-RS8**（Relay系统完整功能）
4. **COM3-COM7**（潜在错误检测）
5. **TE16/TE17/LE12/LE13**（HSR/PRP兼容性，如需）

建议车载开发团队基于本PICS表格进行实现检查清单的定制，根据具体应用场景选择需要支持的Optional项，并在PICS的Support列中明确记录实现状态。
