1. 协议概述与目标

IEEE 802.1CB-2017 定义了帧复制与消除可靠性 (Frame Replication and Elimination for Reliability, FRER) 机制，用于降低以太网中由于设备故障导致的丢包概率。FRER 不创建冗余路径，仅负责在已有冗余路径上进行帧的复制、标识和去重。

核心思想：在发送端对数据包进行序列编号并复制到多条路径传输，在接收端或中间节点根据序列号消除重复包。

1.1 FRER 的目标与约束

目标说明
Packet replication复制数据包，通过多条路径发送，降低丢包概率
Multicast/Unicast支持单播和组播路径
Intermittent Streams任意路径上同时最多只有1个包在传输
Bulk Streams路径上可同时有多个包在传输
Flexible positioningFRER 功能可部署在端系统、中继系统或代理系统中
Latent error detection检测某条冗余路径静默失效的情况
Backward compatibility支持与非 FRER 感知设备共存
Zero congestion loss与 TSN/AVB 等零拥塞丢失机制兼容
明确非目标：
• In-order delivery：FRER 不保证 Compound Stream 的包按原始顺序到达。如果路径长度差异大，即使各 Member Stream 内部有序，合并后也可能乱序。若需要保序，需要在上层或外部增加重排序缓存。

2. 核心概念

2.1 关键术语

术语定义
Compound Stream逻辑上的完整数据流，由多个 Member Stream 组成
Member StreamCompound Stream 的物理分量，在单条路径上传输
stream_handle本地整数，标识一个 Stream。仅本地有效，不体现在报文字段中
sequence_number无符号整数，标识同一 Compound Stream 中包的传输顺序
in-facing / out-facing相对于端口的方向：in-facing=接收侧(ingress)，out-facing=发送侧(egress)

2.2 Stream 服务子参数 (6.1)

Stream identification 服务接口包含以下关键子参数：

  • stream_handle：整数，标识包所属的 Stream
  • sequence_number：无符号整数，标识包在 Compound Stream 中的顺序
sequence_number 可以由 Stream identification function 编码/解码，也可以由独立的 Sequence encode/decode function (如 R-TAG) 处理。

3. Stream Identification (流识别)

Stream Identification 是 FRER 的前提，负责将接收到的数据包映射到 stream_handle，并在发送时根据 stream_handle 修改包内容（如添加/删除 tag、修改 MAC 地址等）。

3.1 四种 Stream Identification 方法

方法匹配字段被动/主动Rtl 设计影响
Null Stream ID (6.4)无匹配，所有包都属于同一 Stream被动最简单，无需匹配逻辑
Source MAC + VLAN (6.5){Source MAC, VLAN ID}被动需要解析 MAC SA 和 VLAN tag
Active Destination MAC + VLAN (6.6){Dest MAC, VLAN ID}，可修改目的MAC/VLAN主动需要查表+改写逻辑
IP Stream ID (6.7){IP Source, IP Dest, DSCP, Protocol, Port}被动需要深解析到 L3/L4

RTL 设计提示：Stream Identification 模块

  • 查表结构：需要一个可配置的 CAM/TCAM 表 (tsnStreamIdEntry)，支持按不同字段匹配
  • 流水线：建议采用报文头解析流水线，逐级提取 {DMAC, SMAC, VLAN, IP, Port}，最后一级查表输出 stream_handle
  • 主动修改：Active DMAC+VLAN 方式需要在查表后修改报文头，注意 checksum 重算
  • Default：未匹配到的包，stream_handle = null，sequence_number = null

5. Sequence Generation (序列生成)

5.1 功能描述

Sequence Generation Function 为每个 Stream 的每个发送包分配一个递增的 sequence_number。每个端口每个 stream_handle 每个方向 (in-facing/out-facing) 最多只有一个 Sequence Generation 实例。

5.2 内部变量

变量类型/范围说明
GenSeqSpace常量 = 65536sequence_number 空间大小 (16-bit)
GenSeqNum0 ~ 65535当前待发送的序列号，发完后 +1 (mod 65536)

5.3 事件

事件触发
BEGIN全局复位，触发 SequenceGenerationReset()
DATA_REQUEST上层请求发送包，触发 SequenceGenerationAlgorithm()
SEND_DATA序列号分配完成后，将包下发到下一层

5.4 伪代码 (RTL 可直接翻译)

// ========== SequenceGenerationReset() ==========
void SequenceGenerationReset() {
    GenSeqNum = 0;
    frerCpsSeqGenResets++;   // 计数器
}

// ========== SequenceGenerationAlgorithm() ==========
void SequenceGenerationAlgorithm() {
    unsigned int sequence_number = GenSeqNum;
    if (GenSeqNum >= (GenSeqSpace - 1))
        GenSeqNum = 0;
    else
        GenSeqNum = GenSeqNum + 1;
    SEND_DATA;  // Pass packet & sequence_number down stack
}

RTL 设计提示：Sequence Generation

  • 核心逻辑：每个 stream_handle 维护一个 16-bit 计数器 GenSeqNum，接收到发送请求时输出当前值并自增
  • Wrap-around：计数器从 65535 回到 0，RTL 中直接用 16-bit 无符号加法自然回绕
  • 多 Stream 支持：需要为每个 stream_handle 维护独立的 GenSeqNum，可用 RAM/RegFile 存储
  • 表项配置：frerSeqGenStreamList 决定哪些 stream_handle 需要序列生成，frerSeqGenDirection 决定方向
  • 复位：软件写 frerSeqGenReset (或全局 BEGIN) 时，对应计数器清零
  • 面积优化：若系统支持 N 个 Stream，则需要 N x 16-bit 寄存器/存储器

6. Sequence Recovery (序列恢复)

Sequence Recovery Function 运行在合并后的 Compound Stream 上，负责消除来自不同 Member Stream 的重复包。

6.1 两种应用场景

场景说明适用算法
Intermittent Stream任意路径上同时最多只有1个包在传输，seq_num 差值不会超过1MatchRecoveryAlgorithm (frerSeqRcvyHistoryLength=1 时 Vector 也适用)
Bulk Stream路径上可同时有多个包，seq_num 差值可能很大VectorRecoveryAlgorithm (frerSeqRcvyHistoryLength >= 2)

6.2 Base Recovery Function 通用变量 (7.4.3)

变量类型/范围说明
RecovSeqSpace常量 = 65536序列号空间
RecovSeqNum0 ~ 65535最近一次接受的序列号
SequenceHistory[]位向量，长度 = frerSeqRcvyHistoryLength记录最近 HistoryLength 个序列号的接收状态
RemainingTicks无符号整数超时倒计时，减到0触发 RECOVERY_TIMEOUT
TicksPerSecond>= 100Tick 频率，由实现提供
TakeAnyBoolean复位后第一条包无条件接受

6.3 通用事件

事件触发
BEGIN全局复位，触发 SequenceRecoveryReset()
DATA_INDICATION下层收到包，触发 Vector/Match Recovery Algorithm
RECOVERY_TIMEOUTRemainingTicks 减到 0，触发 SequenceRecoveryReset()
PRESENT_DATA算法判定包有效，向上层递交

6.4 SequenceRecoveryReset 伪代码

void SequenceRecoveryReset() {
    if (frerSeqRcvyAlgorithm == Vector_Alg) {
        RecovSeqNum = RecovSeqSpace - 1;   // = 65535
        for (i = 0; i < frerSeqRcvyHistoryLength; i++)
            SequenceHistory[i] = 0;
    }
    TakeAny = true;
    frerCpsSeqRcvyResets++;
}
MatchRecoveryAlgorithm 不需要 SequenceHistory，因此 reset 时只需设置 TakeAny。

6.5 VectorRecoveryAlgorithm (7.4.3.4)

适用于 Bulk Streams，使用滑动窗口 (SequenceHistory) 记录最近 frerSeqRcvyHistoryLength 个序列号的接收状态。

核心逻辑

  1. 检查 sequence_number 是否为有效值（不是 frerSeqRcvyInvalidSequenceValue）
  2. 计算有符号差值 delta = sequence_number - RecovSeqNum（模 65536 运算）
  3. 如果 TakeAny == true：接受该包，设置 RecovSeqNum = sequence_number，SequenceHistory[0]=1，TakeAny=false
  4. 如果 delta >= HistoryLength 或 delta <= -HistoryLength：丢弃（Rogue packet）
  5. 如果 delta <= 0：检查 SequenceHistory[-delta]，为0则接受（Out-of-order），为1则丢弃（Duplicate）
  6. 如果 delta > 0：新包，接受。先 shift SequenceHistory delta-1 次（补0），再 shift 1 次（补1），更新 RecovSeqNum

伪代码

void VectorRecoveryAlgorithm() {
    unsigned int sequence_number;
    // === 检查序列号有效性 ===
    if (sequence_number == frerSeqRcvyInvalidSequenceValue) {
        frerCpsSeqRcvyTaglessPackets++;
        if (frerSeqRcvyTakeNoSequence) {
            frerCpsSeqRcvyPassedPackets++;
            frerCpSeqRcvyPassedPackets++;
            RemainingTicks = ((frerSeqRcvyResetMSec * TicksPerSecond) + 999) / 1000;
            PRESENT_DATA;
        } else {
            frerCpsSeqRcvyDiscardedPackets++;
            frerCpSeqRcvyDiscardPackets++;
        }
        return;
    }

    // === 计算有符号差值 (modulo RecovSeqSpace) ===
    int delta = (sequence_number - RecovSeqNum) & (RecovSeqSpace - 1);
    if (0 != (delta & (RecovSeqSpace / 2)))
        delta = delta - RecovSeqSpace;
    // 结果范围: -(RecovSeqSpace/2) <= delta <= (RecovSeqSpace/2 - 1)

    // === 复位后第一条包 ===
    if (TakeAny) {
        TakeAny = false;
        SequenceHistory[0] = 1;
        RecovSeqNum = sequence_number;
        frerCpsSeqRcvyPassedPackets++;
        frerCpSeqRcvyPassedPackets++;
        RemainingTicks = ((frerSeqRcvyResetMSec * TicksPerSecond) + 999) / 1000;
        PRESENT_DATA;
    }
    // === Rogue packet: 超出 History 窗口 ===
    else if (delta >= frerSeqRcvyHistoryLength || delta <= -frerSeqRcvyHistoryLength) {
        frerCpsSeqRcvyRoguePackets++;
        frerCpSeqRcvyDiscardPackets++;
        if (frerSeqRcvyIndividualRecovery)
            RemainingTicks = ((frerSeqRcvyResetMSec * TicksPerSecond) + 999) / 1000;
    }
    // === 老包 (delta <= 0): 检查是否已接收 ===
    else if (delta <= 0) {
        if (0 == SequenceHistory[-delta]) {
            // 未见过，接受 (out-of-order)
            SequenceHistory[-delta] = 1;
            frerCpsSeqRcvyOutOfOrderPackets++;
            frerCpsSeqRcvyPassedPackets++;
            frerCpSeqRcvyPassedPackets++;
            RemainingTicks = ((frerSeqRcvyResetMSec * TicksPerSecond) + 999) / 1000;
            PRESENT_DATA;
        } else {
            // 重复包，丢弃
            frerCpsSeqRcvyDiscardedPackets++;
            frerCpSeqRcvyDiscardPackets++;
            if (frerSeqRcvyIndividualRecovery)
                RemainingTicks = ((frerSeqRcvyResetMSec * TicksPerSecond) + 999) / 1000;
        }
    }
    // === 新包 (delta > 0): 正常前进 ===
    else {
        if (delta != 1)
            frerCpsSeqRcvyOutOfOrderPackets++;
        while (0 != (delta = delta - 1))
            ShiftSequenceHistory(0);  // 补 "未收到"
        ShiftSequenceHistory(1);       // 当前包标记 "已收到"
        RecovSeqNum = sequence_number;
        frerCpsSeqRcvyPassedPackets++;
        frerCpSeqRcvyPassedPackets++;
        RemainingTicks = ((frerSeqRcvyResetMSec * TicksPerSecond) + 999) / 1000;
        PRESENT_DATA;
    }
}

// ========== ShiftSequenceHistory ==========
void ShiftSequenceHistory(int newZeroValue) {
    if (0 == SequenceHistory[frerSeqRcvyHistoryLength - 1])
        frerCpsSeqRcvyLostPackets++;   // 滑出窗口的位是0，表示该seq_num从未收到
    for (i = frerSeqRcvyHistoryLength - 1; i != 0; i--)
        SequenceHistory[i] = SequenceHistory[i - 1];
    SequenceHistory[0] = newZeroValue;
}

RTL 设计提示：VectorRecoveryAlgorithm

  • SequenceHistory 存储：使用一个 frerSeqRcvyHistoryLength 位的寄存器/存储器。最小支持2位，典型值如16/32/64
  • delta 计算： 
    delta = (seq_num - RecovSeqNum) & 16'hFFFF;
if (delta[15]) delta = delta - 16'd65536;  // 有符号化
    结果范围为 -32768 ~ +32767
  • History 移位：当 delta > 1 时，需要连续 shift delta 次。若 delta 可能很大，可用 barrel shifter 一次完成多位移位：SequenceHistory = (SequenceHistory << delta) | new_bits
  • 丢失检测：ShiftSequenceHistory 中，若最高位(即将移出的位)为0，则 frerCpsSeqRcvyLostPackets++。RTL 中可用组合逻辑判断
  • 超时定时器：RemainingTicks 以 TicksPerSecond 频率递减。建议用独立计数器生成 Tick，每个 recovery 实例维护一个 RemainingTicks 计数器
  • 多 Stream 支持：每个 port + stream_handle + direction 对应一个 recovery 实例，可用 RAM 存储状态 (RecovSeqNum, SequenceHistory, TakeAny, RemainingTicks)
  • 资源估算：假设支持 256 个 Stream，HistoryLength=32，每个实例需要 16(RecovSeqNum) + 32(History) + 1(TakeAny) + ~20(RemainingTicks) = ~69 bits。256 个实例约需 2.2 KB 存储

6.6 MatchRecoveryAlgorithm (7.4.3.5)

适用于 Intermittent Streams，仅记录上一个接受的序列号，新包序列号不同即接受，相同即丢弃。

伪代码

void MatchRecoveryAlgorithm() {
    unsigned int sequence_number;
    // === 检查序列号有效性 ===
    if (sequence_number == frerSeqRcvyInvalidSequenceValue) {
        frerCpsSeqRcvyTaglessPackets++;
        frerCpsSeqRcvyPassedPackets++;
        frerCpSeqRcvyPassedPackets++;
        PRESENT_DATA;
        return;
    }

    // === 复位后第一条包 ===
    if (TakeAny) {
        TakeAny = false;
        RecovSeqNum = sequence_number;
        frerCpsSeqRcvyPassedPackets++;
        frerCpSeqRcvyPassedPackets++;
        RemainingTicks = ((frerSeqRcvyResetMSec * TicksPerSecond) + 999) / 1000;
        PRESENT_DATA;
    }
    // === 序列号匹配 ===
    else {
        int delta = (sequence_number - RecovSeqNum) & (RecovSeqSpace - 1);
        if (delta == 0) {
            // 重复包
            frerCpsSeqRcvyDiscardedPackets++;
            frerCpSeqRcvyDiscardPackets++;
            if (frerSeqRcvyIndividualRecovery)
                RemainingTicks = ((frerSeqRcvyResetMSec * TicksPerSecond) + 999) / 1000;
        } else {
            // 新包
            if (delta != 1)
                frerCpsSeqRcvyOutOfOrderPackets++;
            RecovSeqNum = sequence_number;
            frerCpsSeqRcvyPassedPackets++;
            frerCpSeqRcvyPassedPackets++;
            RemainingTicks = ((frerSeqRcvyResetMSec * TicksPerSecond) + 999) / 1000;
            PRESENT_DATA;
        }
    }
}

RTL 设计提示：MatchRecoveryAlgorithm

  • 极简实现：仅需保存 RecovSeqNum (16-bit) + TakeAny (1-bit) + RemainingTicks，无需 SequenceHistory
  • 判断逻辑：只需判断 sequence_number == RecovSeqNum，相同则丢弃，不同则接受
  • 资源对比：相比 Vector 算法，Match 算法每个实例节省 HistoryLength 位存储，适合资源受限场景
  • 限制：无法检测丢包 (LostPackets)，不支持 Bulk Stream（路径差大于1会误丢弃或误接受）

7. Individual Recovery Function (7.5)

Individual Recovery 作用于单条 Member Stream（而非合并后的 Compound Stream），用于检测并丢弃来自 stuck transmitter 的重复包。它使用与 Base Recovery 相同的算法，但 frerSeqRcvyIndividualRecovery = True。

与 Sequence Recovery 的关键区别：
  • Sequence Recovery 合并多条 Member Stream 并去重，包含 Latent Error Detection
  • Individual Recovery 仅处理单条 Member Stream，不包含 Latent Error Detection
  • Individual Recovery 的 frerSeqRcvyPortList 可以包含多个端口（即跨端口对同一 Stream 做单独去重）
设计建议：在路径汇聚点前，对每条 Member Stream 先做一次 Individual Recovery，可以有效防止 stuck transmitter 污染 Sequence Recovery 的状态机。

8. Latent Error Detection (7.4.4)

Latent Error Detection 检测冗余路径中是否存在静默失效（某条路径完全停止发送，但系统仍以为冗余有效）。它假设正常工作时，n 条路径中有 n-1 条路径的包会被丢弃，即 Discarded ≈ Passed × (n-1)。

8.1 核心算法

// 周期复位 (由 RESET_LATENT_ERROR 事件触发)
void LatentErrorReset() {
    CurBaseDifference = (frerCpsSeqRcvyPassedPackets * (frerSeqRcvyLatentErrorPaths - 1))
                        - frerCpsSeqRcvyDiscardedPackets;
    frerCpsSeqRcvyLatentErrorResets++;
}

// 周期检测 (由 TRIGGER_LATENT_ERROR_TEST 事件触发)
void LatentErrorTest() {
    int diff = CurBaseDifference
             - ((frerCpsSeqRcvyPassedPackets * (frerSeqRcvyLatentErrorPaths - 1))
                - frerCpsSeqRcvyDiscardedPackets);
    if (frerSeqRcvyLatentErrorPaths > 1 && frerSeqRcvyLatentErrorPeriod > 0) {
        if (diff < 0) diff = -diff;
        if (diff > frerSeqRcvyLatentErrorDifference) {
            SIGNAL_LATENT_ERROR;   // 触发告警
        }
    }
}

8.2 管理对象

对象说明
frerSeqRcvyLatentErrorDifference阈值：允许的实际丢弃数与期望丢弃数的偏差
frerSeqRcvyLatentErrorPeriod检测周期（秒），最小建议值 1s
frerSeqRcvyLatentErrorPaths冗余路径数 n
frerSeqRcvyLatentResetPeriod复位周期（秒），用于重置 CurBaseDifference
该算法存在量化误差：若 LatentErrorTest 与 LatentErrorReset 时机不巧，可能需要 2 × frerSeqRcvyLatentErrorDifference 的偏差才能触发告警。

RTL 设计提示：Latent Error Detection

  • 独立定时器：需要两个独立定时器，分别以 LatentErrorPeriod 和 LatentResetPeriod 为周期
  • 乘法器：Passed × (Paths-1) 需要乘法器。若 Paths 为固定值（如2），可用移位/加法代替
  • 计数器位宽：Passed 和 Discarded 计数器需足够宽（标准建议 64-bit @ >650Mbps）
  • 可关闭：frerSeqRcvyLatentErrorPeriod=0 时关闭检测

9. R-TAG (Redundancy Tag) 格式 (7.8)

R-TAG 是 802.1CB 定义的必选 Sequence Encode/Decode 格式，直接插入在 MAC 帧的 payload 最前端。

9.1 R-TAG 格式

字段长度值/说明
EtherType (TPID)2 bytes0xF1C1 (R-TAG EtherType)
Reserved2 bytes传输必须为 0，接收必须忽略
Sequence Number2 bytessequence_number 的低 16 位 (MSB first)

总长度：6 bytes。插入后 MAC 帧 payload 增加 6 字节。

9.2 编码操作 (发送)

  1. 将 sequence_number 的低 16 位写入 Sequence Number 字段
  2. Reserved 字段填 0
  3. 将 6-byte R-TAG 插入到 mac_service_data_unit 的最前端

9.3 解码操作 (接收)

  1. 检查 mac_service_data_unit 前 2 字节是否等于 0xF1C1
  2. 若匹配且长度 >= 6 字节：
    • 移除前 6 字节
    • 将 Sequence Number 字段提取到 sequence_number 子参数
  3. 若不匹配或长度 < 6：
    • sequence_number = frerSeqRcvyInvalidSequenceValue
    • frerCpsSeqEncErroredPackets++
R-TAG 位置注意：R-TAG 位于 payload 最前端，在 VLAN tag 之前。如果帧同时有 VLAN tag 和 R-TAG，顺序为：DMAC | SMAC | R-TAG | VLAN Tag | ...。这与常规 VLAN tag 位置 (DMAC | SMAC | VLAN | Type) 不同。

RTL 设计提示：R-TAG 处理

  • 插入位置：在 MAC 帧的 payload 头部，即 DMAC(6) + SMAC(6) + R-TAG(6) + ...
  • 字节序：Sequence Number 的高字节在前 (octet 4)
  • 流水线：建议在报文解析的第一级检查 EtherType = 0xF1C1，若是则提取 SeqNum 并跳过 6 字节
  • 带宽影响：每帧增加 6 字节，对千兆/万兆网络影响极小
  • 与其他 Tag 共存：需确保 parser 能识别 R-TAG 后紧跟 VLAN tag 的情况 (0xF1C1 后跟 0x8100)

10. Sequence Encode/Decode (7.6)

Sequence Encode/Decode Function 负责在报文中插入/提取 sequence_number。802.1CB 定义了三种格式：

格式要求位置用途
R-TAG (7.8)必选Payload 头部802.1CB 原生格式
HSR Sequence Tag (7.9)可选Payload 头部与 IEC 62439-3 HSR 互通
PRP Sequence Trailer (7.10)可选Payload 尾部与 IEC 62439-3 PRP 互通
三种格式通过 frerSeqEncEncapsType (10.5.1.5) 配置，使用 OUI=00-80-C2 区分。

11. Stream Splitting (7.7)

Stream Splitting Function 将 Compound Stream 拆分为多个 Member Stream。它作用于出端口 (out-facing)，根据 frerSplitInputIdList 匹配 stream_handle，为每个匹配项复制一份包，并将 stream_handle 替换为 frerSplitOutputIdList 中的对应值。

典型应用：Talker 产生一个 Compound Stream (stream_handle=1)，经过 Stream Splitting 后变成两个 Member Stream (stream_handle=10 和 11)，分别发往两个不同端口，各自再经过 Sequence Generation 和 R-TAG 编码。

RTL 设计提示：Stream Splitting

  • 包复制：需要报文缓存和描述符复制机制，确保同一包内容被发送到多个端口
  • stream_handle 重写：输出时根据查表结果修改描述符中的 stream_handle
  • 与 Sequence Generation 配合：Split 后的各 Member Stream 共享同一个 Sequence Generation 实例（即 seq_num 一致）

所有计数器达到最大值后回绕到 0。标准假设管理实体读取频率足够高，不会错过超过一次回绕。计数器位宽应足够大，使得回绕时间至少为 1 分钟。

RTL 设计提示：Counters

  • 位宽选择：千兆以上链路建议使用 64-bit 计数器。若仅统计低速流，32-bit 可能足够
  • 原子性：计数器递增操作需要对软件读取原子。可用影子寄存器或双缓冲机制
  • 多端口统计：若 Sequence Recovery 实例化在转发平面中央（而非每端口），丢弃一个包可能需要同时递增多个端口的计数器
  • 计数器存储：大量计数器需要专用 SRAM 区域，建议按 (port, stream, counter_type) 索引

14.3 时序与性能考量

  • 最低时钟：TicksPerSecond >= 100 Hz，建议用 1KHz 或更高精度定时器
  • 报文处理延迟：Sequence Recovery 需要完整解析 sequence_number 后才能判定通过/丢弃，不适合 cut-through（至少对丢弃的包）
  • 流水线深度：Stream Identification + Sequence Recovery 可能需要 3~5 级流水线，在 156.25MHz 下对 10G 线速是可接受的
  • 存储器需求：核心状态存储 = N_streams × (RecovSeqNum + History + Timer + Flags)。例如 512 Stream × 80 bits = 40 Kbit ≈ 5 KB

14.4 复位策略

  • 全局复位 (BEGIN)：硬件复位时所有状态清零
  • 软件复位 (frerSeqRcvyReset)：写 True 触发对应实例的 SequenceRecoveryReset()
  • 超时复位 (RECOVERY_TIMEOUT)：RemainingTicks 减到 0 自动复位。这是防 stuck 的关键机制

14.5 边界条件处理

场景处理
Sequence number wrap-around (65535->0)自然处理，delta 计算用有符号模运算
无序列号的包 (InvalidSequenceValue)由 frerSeqRcvyTakeNoSequence 决定：True=通过，False=丢弃
第一条包到达 (TakeAny)无条件接受，建立 RecovSeqNum 基准
路径切换导致突发Vector 算法会接受窗口内所有包，可能短暂双倍速率输出
Stuck transmitter 重复同一包Vector/Match 都会丢弃重复，但绕回后可能误判。建议配合 Individual Recovery

总结

IEEE 802.1CB-2017 FRER 协议通过序列编号 + 帧复制 + 去重机制，为以太网提供设备故障级别的可靠性保障。RTL 实现的核心在于：

  1. Stream Identification：灵活可配置的报文分类器
  2. Sequence Generation：简单的 16-bit 循环计数器
  3. Sequence Recovery：基于滑动窗口 (Vector) 或单值匹配 (Match) 的去重状态机
  4. R-TAG：6-byte 报文头插入/提取
  5. 计数器与超时机制：完善的统计和故障恢复能力
最小可裁剪实现：若仅需要基本 FRER 功能，可只实现：Null Stream ID + R-TAG + Sequence Generation + Match Recovery (HistoryLength=1)。这覆盖了 Talker/Listener 的核心需求，面积最小。
