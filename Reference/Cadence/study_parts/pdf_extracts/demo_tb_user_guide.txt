1. Introduction
This document defines the Cadence GEM_GXL IP Demo Testbench which has been developed to
enable the customer to run simple test cases that demonstrate the Cadence GEM_GXL IP base
features. These test cases are abstracted to promote easier understanding of how to program the
Cadence GEM_GXL IP and allow reuse within a higher level verification environment. This testbench
can also be used as a starting point for the customer to integrate the Cadence VIP relating to the
Cadence IP into their system verification environment.

Please note that the Cadence VIP Catalogue (VIPCAT) is an essential component of this Demo
Testbench and must be installed and available on the customer’s systems.

This section gives a generic overview and displays tool requirements for running the GEM_GXL Demo
Testbench. In addition:

          Section 2 (Architectural Overview) details the architecture of the GEM_GXL Demo Testbench.
          Section 3 (Package and Directory Structure) gives information on how installing and running
           the GEM_GXL Demo Testbench. The directory structure of the environment is also highlighted
           and notable files location discussed.
          Section 4 (Use Cases/Demo Cases) introduces available test cases and related code
           documentation which can be extracted using NaturalDocs and Doxygen tools.
          Section 5 (Known Issues) reports for recognized issues inside the GEM_GXL Demo
           Testbench.

2. Architectural Overview
This section describes the Cadence GEM_GXL IP Demo Testbench common architecture which may
be shared between variants of the Cadence GEM_GXL IP. Where multiple variants exist, there is a
subsection for each IP type.

The Demo Testbench may be delivered with either UVM SV tests or C tests as illustrated by the right-
hand columns of Figure 1. Offering these options promotes reuse of the tests in a system context. Both
options share a common UVM environment. The UVM test layers or C test layers interface to the
common UVM environment through abstraction layers, which in the case of the C test layer also includes
C-DPI1 calls to transition over the language barrier. Figure 1 also illustrates reuse in a CPU-based SoC
verification environment on the left-hand column of the diagram (see [6]).

2.1.      Common UVM Environment
The Demo Testbench is configured and customized depending on the provided type of Cadence
GEM_GXL IP, however there are some constant factors:

       1. The Demo Testbench uses the UVM class libraries and associated methodology. The Demo
          Testbench is encapsulated as a UVC called cdn_gem_demo and can be found in the following
          directory:

          <DEMO TB INSTALL PATH>/verif/uvc_lib/cdn_gem_demo
       2. The Cadence VIP is used for System bus interfaces (e.g. AXI, APB) and protocol interfaces
          (e.g. ENET). The VIP is wrapped up as UVCs to make them UVM compatible. These UVCs
          can be found in the <DEMO TB INSTALL PATH>/verif/uvc_lib directory and are named
          cdn_*_vip; where * is the name of the protocol (e.g. enet/axi/apb).
              a. NaturalDocs HTML documentation is available for these VIP UVC wrappers. Please
                 refer to Section 4 for more information.
              b. The Cadence VIP uses the SV interface and SV config object approach instead of the
                 SOMA and Verilog module because it works better with UVM.

          please refer to the GEM_GXL IP documentation [3][4].

2.2.       UVM Test Layer
The UVM test layer uses UVM class libraries and associated methodology [2], except that constrained
random verification is not used but instead a directed testing approach is used to ensure the demo
tests/cases work as required. A hierarchical approach to test sequences is used to enable clarity within
test cases.

          All SV tests are located in the cdn_gem_demo/sve/tests sub-directory. Descriptions of the
           tests and all UVM-SV elements are available in HTML via NaturalDocs. For more information,
           refer to Section 4.
          All sequences libraries are located in the cdn_gem_demo/sv subdirectory.

2.3.       C Test Layer
The C test layer is provided to promote reuse in a CPU driven system level environment. The C test
layer utilizes the same Cadence Core Driver (aka Bare Metal Driver) which is provided with the full IP
product for SW development. The core driver provides a simple and consistent API for test cases. It also
provides a Hardware Abstraction Layer (aka CPS) which may be adapted to suit different system-level
platforms.

          All C based test are located in the cdn_gem_demo/sve/tests_c subdirectory. Descriptions
           of the tests are available in HTML via Doxygen. For more information, refer to Section 4.
          C register headers are included and used within the C test cases. These headers are generated
           from IPXACT and may be found in the cdn_gem_demo/c/CoreDriver/include directory.
          The Core Driver (aka Bare Metal Driver) is normally provided as part of a full IP release, or as
           a separate SW-only delivery. When it is part of a full IP release, this driver is automatically
           found by the Demo Testbench Makefile, however it may be overridden via the
           CDN_DEMO_SW_PATH_OVERRIDE Makefile command line option (not required to be set in
           full IP release).

The following list summarizes the high-level functionalities of the Demo Testbench as contained in the
various blocks:

          Clock and reset signals to the DUT/testbench are generated through respective UVCs.

© Cadence Design Systems, Inc                                      Cadence Confidential                                                          11 of 27
                                                                       Cadence GEM_GXL Demo Testbench
                                                                                           User Guide




       The default system busses for programming and data structures are APB and AXI, respectively.
        To allow for an easy replacement with proprietary busses, adapter modules are provided.
       Test sequences run on a virtual sequencer to allow control of the various interface in one place.
       For the UVM test layer, tests follow the standard methodology and are provided to demonstrate
        basic functionalities.
            o   The system memory is emulated within the AXI VIP and handled using its interface.
            o   Separate data scoreboards are provided for transmission (Tx) and receive (Rx) paths
                of the IP. These are configurable from env/sequences and thought to be simple in
                nature, performing a byte-to-byte comparison between the Ethernet and AXI packets
                raw data.
       For the C test layer, each test is implemented as a main function which is called through the
        base sequence from the UVM world. Only one C test is compiled for each run.
            o   System memory is allocated in the tests and handled through the memory adapter and
                the C-DPI interface from the underlying UVM environment. To this extent, AXI VIP
                callbacks are used to modify the content of the AXI transaction with that of the actual C
                memory.
            o   C tests do not rely on the UVM data scoreboard and self-checking mechanisms are
                directly implemented within each of them in order to reuse this feature at system level.
       For a list of available tests with brief description please refer to section 4. For more detailed
        information about UVM and C code please refer to documentation as highlighted in sections 4.1
        and 4.2.
       For each of the main physical interface in the DUT – i.e. AXI, APB and ENET – a respective
        SystemVerilog interface is provided. Signals not present in one of the previous are allocated
        into a miscellaneous signals interface. All interfaces are connected to the DUT through a DUT
        wrapper.

Support for interrupt monitoring is added in the C/UVM framework. Nevertheless, its operation is not
demonstrated in the current GEM_GXL Demo Testbench release.

Please note that this user guide only provides a description of the Demo Testbench in relation to the
GEM_GXL IP, which is an advanced and configurable Ethernet controller [1]. It is intended that a full
description of the GEM_GXL features is given elsewhere and to this extent reference should be made
to the proper documentation [3][4].

3.3.    Running a Simulation on a Standalone Package
Please note that in order to run the GEM_GXL demo TB a UVM_REG SystemVerilog model is needed.
This is provided within the GEM_GXL IP package (full IP delivery) or demo TB package (standalone
delivery) for the default design configuration. If the end user desires to run the demo TB on a custom
configuration should contact Cadence to provide the correct UVM_REG model.

This section explains how to run a simulation within the GEM_GXL Demo Testbench using a flexible
Makefile, which is the recommended approach for a standalone package delivery. For a full IP
package please refer to the release notes. The Makefile is located inside the cdn_demo UVC at
cdn_demo/sve.

NOTE: it is assumed that the Cadence Incisive and Cadence VIPCAT have all been installed and set
up with all relevant environment variables for these tools configured in your current shell. As a minimum,

3.6.     RAM Integration Tests
Please note that this feature is not yet available in the GEM_GXL Demo Testbench and will be added
in future releases. This will comprise two methods: i) test cases to exercise the RAM interfaces; ii) swap
part of the DUT for a “RAM Integration Stub” that fully exercises all RAM interfaces.

The Cadence IP is provided with generic models for RAMs which are typically replaced by a customer’s
own technology specific libraries. Please see the full IP documentation for details on RAMs and
replacement. After such replacement the customer should verify correct integration of the RAMs.

To assist the customer in this verification, a suite of RAM integration tests is provided as part of the
Demo Testbench. These tests are run as per any other test using the Makefile or regression scripts,
with no additional command line options required and with the same pass/fail status reporting.

These tests aim to prove both connectivity and functionality checks for RAMs which are directly attached
to the IP, whether this is within the IP integration layers or within the customer’s own design.

3.6.1.   Current RAM Integration Limitations
There will be some limitations to RAM integration testing using the Demo Testbench. Due to the fact
that the Demo Testbench tests and sequences are supposed to demo the basic working operation of
the design IP, all traffic conditions that would exhaustively cover all RAM conditions are not possible to
hit. Adding such complexity to the Demo Testbench would significantly increase the complexity of the
testbench and as such make it very difficult to use as a vehicle for customer understanding of the
programming model required to operate the design. This overall limitation will remain.

The following VIP-related warnings are known and will be herein documented:

// When AXI VIP spec is set to AXI4
reporter [cdnAxiUvmConfig check] __internal__awlockCheck3 failed: awlock should be 1
bits when (spec_ver_AMBA4 || spec_ver_AMBA5)
reporter [cdnAxiUvmConfig check] __internal__arlockCheck3 failed: arlock should be 1
bits when (spec_ver_AMBA4 || spec_ver_AMBA5)

// When AXI VIP spec is set to AXI3
reporter [cdnAxiUvmConfig check] __internal__awlenCheck3 failed: awlen in AXI3 mode
should be up to 4 bits
reporter [cdnAxiUvmConfig check] __internal__arlenCheck3 failed: arlen in AXI3 mode
should be up to 4 bits

The above warnings are fired because the AXI interface in the GEM_GXL IP is not configurable, i.e. it
complies with both the AXI3 and AXI4 standards simultaneously. This results in AXI VIP configuration
warnings, since the awlock, arlock, awlen and arlen signals are of different size between the two
spec versions.

UVM_WARNING: uvm_test_top.sve.demo_env.axi_env.active_slave.monitor

<some id>

The above warnings are fired when the AXI VIP slave agent could not create a legal VIP transaction
from the input and the item is discarded. This may happen in C-based tests. Nevertheless, their
functionality is not affected.

Appendix A.Customer Modifications
The Demo Testbench provides some hooks to enable limited customisations of the DUT and associated
verification components. These should be used with care and it is the customer’s responsibility to verify
any such customisations.

A.1     Replacing the System Side Busses with Alternative UVCs
It is possible that customers will want to replace the system side busses with their own proprietary
interfaces. Typically, this would be done by adding bridges to the IP RTL on top of AXI and APB as well
as adding UVCs to the demo TB. To make this simpler for our customers we have done the following:

1. For the DUT APB Slave interfaces (APB Master VIP), UVM_REG is used to abstract register
   reads/writes, thus only the register adapter file (cdn_demo_sys_bus_reg_adapter.sv) needs
   to be replaced or modified. As a minimum the customer should re-implement the following functions:
           read(): only applicable for C tests to trigger an APB Master VIP read.
           write(): only applicable for C tests to trigger an APB Master VIP write.
           reg2bus(): only applicable for UVM tests to convert UVM_REG operation to APB Master
            transaction.
           bus2reg(): applicable to both UVM and C tests to monitor APB Master transaction.
2. For the DUT AXI Master interface (AXI Slave VIP), a memory model is used to emulate attached
   system memory and is located within the AXI Slave VIP for UVM tests and within the C test layer
   when C tests are used. The system memory model must be accessible from both test layer side
   and VIP side. As such all reads/writes to the system memory model are encapsulated into a single
   file called cdn_demo_sys_bus_memory_adapter.sv. As a minimum the customer should re-
   implement the following functions:
           read_mem(): only applicable for UVM tests to fetch data from system memory model
            located within the AXI Slave VIP.
           write_mem(): only applicable for UVM tests to push data into system memory model
            located within the AXI Slave VIP.
           write_cdn_axi_uvm_driver_BeforeSendResponse(): applicable for C and UVM
            tests to fetch data from the system memory model and provide to AXI Slave VIP on callback
            from VIP after AXI address phase. Data returned is applied to the data fields at the AXI data
            phase.
           write_cdn_axi_uvm_driver_Ended(): applicable for C and UVM tests to push data
            from AXI Slave VIP into the system memory model upon callback from VIP at end of AXI
            transaction. AXI write data is written at the end of the transaction.
3. Control knobs are provided to switch the APB and AXI VIP from active to passive or else to disabled
   completely. Customer should change the following variables in the Demo Testbench config object
   (cdn_demo/sv/cdn_demo_config_object.sv):
           has_active_apb – set to 0 to change APB VIP to passive monitor.
           has_active_axi – set to 0 to change AXI VIP to passive monitor.
           has_passive_apb – optionally set to 0 to disable APB VIP.
           has_passive_axi – optionally set to 0 to disable AXI VIP.
