1. Introduction
Besides conventional UVM-based tests, the GEM_GXL Demo Testbench is provided with C tests in
order to demonstrate basic health checking of the IP using a software-oriented approach. This
application note contains details on how a customer can reuse the C layer into a CPU-based SoC VE,
taking the Demo Testbench as an example.

With reference to Figure 1, three flows are supported to run in the GEM_GXL Demo Testbench:

      1. UVM-SV simulations: this is the conventional way of running UVM tests and will be not further
         addressed here.
      2. C-based simulations w/o the core driver: this flow demonstrates how to use simple C stimulus.
      3. C-based simulations w/ the core driver: this flow demonstrates how core driver tests (bare-
         metal architecture) can be integrated.

The C flows show a software-based testing approach and how it can be reused at system level. This is
promoted by conveniently setting the APIs that connects the tests to the relative VE. Using these APIs,
C tests are made generic and can run on top of both the GEM_GXL Demo Testbench UVM-SV VE and
an SoC VE. This concept has been proved using Cadence CSP1, to which reference is made throughout
this document.

The reusable C code uses three APIs: Demo Testbench, CPS2 and CSP. The CPS API represents a
platform-specific code that connect a given Cadence driver to the rest of the underlying system [4][5].
Not all of the features of CPS are required to operate the GEM_GXL Demo Testbench. The CSP API
provides functions for the tests to call in order to communicate with the underlying VEs.

The CPS and CSP APIs must be shared between whichever VE desires to run the GEM_GXL Demo
Testbench reusable C code. In order to do this, a VE-dependent implementation must be provided.
Please note that the customer will be responsible of VE-dependent code implementation in his own VE,
in order to accommodate CPS and CSP APIs. However, the implementation burden is contained and
examples are given in the GEM_GXL Demo Testbench package for the UVM-SV VE and in this
document for the GEM_GXL Demo Testbench Cadence CSP VE.

2.1. C Layer Reuse in UVM-SV
C tests run over the UVM-SV VE using the Demo Testbench API. In addition, C tests exploit an
implementation of some functions in the CPS and CSP API. These use several import/export calls
across the C/SV language barrier using the C-DPI3 interface.

The most important functions in the Demo Testbench API are:

       cdn_demo_write*: declared in cdn_demo.h, implemented in cdn_demo.c. Used from the
        UVM   world  to   write   the   C-allocated  AXI   memory    (C-DPI   import    in
        cdn_demo_module_top_c_dpi.sv).
       cdn_demo_read*: declared in cdn_demo.h, implemented in cdn_demo.c. Used from the
        UVM   world  to   read    the   C-allocated  AXI   memory    (C-DPI  import    in
        cdn_demo_module_top_c_dpi.sv).
       csp_demo_write*:         declared   in     cdn_demo.h,        implemented       in
        cdn_demo_module_top_c_dpi.sv. Used from the C world to write APB registers in UVM
        (DPI-C export from cdn_demo_module_top_c_dpi.sv).
       csp_demo_read*:         declared    in    cdn_demo.h,       implemented        in
        cdn_demo_module_top_c_dpi.sv. Used from the C world to read APB registers in UVM
        (C-DPI export from cdn_demo_module_top_c_dpi.sv).
       cdn_demo_printf_*: declared in cdn_gem_demo.h, implemented in cdn_gem_demo.c.
        Wrap around csp_printf_* and allows them to print a formatted string.

The functions needed from the CPS API are:

       CPS_UncachedWrite32: performs a 32-bit uncached write access to the memory. Declared
        in cdn_demo.h, implemented in cdn_demo.c. Since the core driver uses this function to
        access both descriptors and registers, the provided implementation use a function pointer
        (fptr_is_addr_inside_hw_map), which is attached to is_addr_inside_hw_map.
       CPS_UncachedRead32: performs a 32-bit uncached read access to the memory. Declared in
        cdn_demo.h, implemented in cdn_demo.c. Since the core driver uses this function to access
        both descriptors and registers, the provided implementation use a function pointer
        (fptr_is_addr_inside_hw_map), which is attached to is_addr_inside_hw_map.
       CPS_UncachedWrite16: performs a 16-bit uncached wirte access to the memory. Declared
        in cdn_gem_demo.h, implemented in cdn_gem_demo.c.
       CPS_UncachedRead16: performs a 16-bit uncached read access to the memory. Declared in
        cdn_gem_demo.h, implemented in cdn_gem_demo.c.
       CPS_WritePhysAddress32: writes a 32-bit address value to memory, bypassing the cache.
        Declared in cdn_gem_demo.h, implemented in cdn_gem_demo.c.

The functions needed from the CSP API are:

       csp_write32: employed for APB write accesses. Declared in cdn_demo.h, implemented in
        cdn_demo.c. Wraps around csp_demo_write32, which is a C-DPI export from
        cdn_demo_module_top_c_dpi.sv.
       csp_read32: employed for APB read accesses. Declared in cdn_demo.h, implemented in
        cdn_demo.c. Wraps around csp_demo_read32, which is a C-DPI export from
        cdn_demo_module_top_c_dpi.sv.

2.2. C Layer Reuse in SoC
In order for C tests to be reused, the function listed in section 2.1 for the CPS and CSP APIs need a C
declaration/implementation in the SoC VE. For the GEM_GXL Demo Testbench Cadence CSP VE, this
is reported in the following.

The needed CPS functions are declared in cps.h and implemented in cps.c as:

/* cps.h */

#ifndef _CPS_H_
#define _CPS_H_

#include <stdint.h>

extern   uint16_t CPS_UncachedRead16(volatile uint16_t* address);
extern   uint32_t CPS_UncachedRead32(volatile uint32_t* address);
extern   void CPS_UncachedWrite16(volatile uint16_t* address, uint16_t value);
extern   void CPS_UncachedWrite32(volatile uint32_t* address, uint32_t value);
extern   void CPS_WritePhysAddress32(volatile uint32_t* location, uint32_t addrValue);

#endif




/* cps.c */

#include   <stdio.h>
#include   <stdlib.h>
#include   <stdint.h>
#include   <string.h>
#include   “cps.h”

uint16_t CPS_UncachedRead16(volatile uint16_t* address) {
    return *address;
}

uint32_t CPS_UncachedRead32(volatile uint32_t* address) {
    return *address;
}

void CPS_UncachedWrite16(volatile uint16_t* address, uint16_t value) {
    *address = value;
}

void CPS_UncachedWrite32(volatile uint32_t* address, uint32_t value) {
    *address = value;
}

void CPS_WritePhysAddress32(volatile uint32_t* location, uint32_t addrValue) {
    *location = addrValue;
}




The needed CSP functions are contained in csp.h. The function csp_delay_us is CPU-specific and
hence its implementation cannot be shown in detail here. It is left to the customer to find a suitable
implementation for his own SoC-VE as per CSP API specifications.

#ifndef _CSP_H_
#define _CSP_H_

#include “cps.h”

#define csp_read32(addr) \
    (*((volatile uint32_t *)(addr)))

#define csp_write32(addr, data) \
    *((volatile uint32_t *)(addr)) = (data)

#define csp_printf(format, ...) \
    printf(format, ##__VA_ARGS__)

#define csp_printf_error(format, ...) \
    csp_printf("ERROR: " format, ##__VA_ARGS__)

#define csp_printf_warning(format, ...) \
    csp_printf("WARNING: " format, ##__VA_ARGS__)

#define csp_printf_info(format, ...) \
    csp_printf("INFO: " format, ##__VA_ARGS__)

void csp_delay_us(uint32_t us);

#endif
